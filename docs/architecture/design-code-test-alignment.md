# 设计文档、实现与回归测试的统一

> 适用范围：`docs/architecture/plan/` 下的设计文档、`api/` `cpgateway/` `web/` `scripts/` 的实现、`test-items/` 的回归用例与追踪表
> 状态：2026-10-14 提出并开始执行，步骤 1–3 已完成，步骤 4（按功能域对齐）待开始，进度见 §4

## 1. 目标

任何一个对外可用的功能，都能顺着同一条线找到三样东西，并且三者说法一致：

```
设计（或行为说明）的章节  ↔  回归用例的步骤与预期  ↔  代码  ↔  追踪表里这一行的测试结果
```

连接点是追踪表 `test-items/回归功能追踪.csv`：每行一个子功能，写明设计依据、回归用例、覆盖步骤、最近执行与结果。

## 3. 做法

### 3.1 先定清楚谁说了算

1. **给设计文档分级**：`docs/architecture/plan/` 加索引（`index.md`，文档站拿它当目录首页），每份标「维护中 / 历史（被什么取代）/ 作废」。只有「维护中」的参与统一；历史文档不改正文，只在开头注明被什么取代。
2. **没有设计的功能域补一页行为说明**：不必是完整设计，写清接口、业务规则、拒绝条件、权限、与其他功能的关系就够。从现有代码与 `CLAUDE.md` 的约定整理，经负责人确认后作为这个域的设计依据。
3. **分歧的裁决**：默认以设计意图为准；负责人确认实现更合理时改设计。每条分歧都要有人拍板，不能由写用例的人按代码默认。

### 3.2 一次性对齐（按功能域串行，一次一个）

每个功能域做三方对照，产出一张分歧清单，每条注明处理方式：

| 分歧类型 | 处理 |
|---|---|
| 设计有、代码没有 | 补实现，或在设计里标「没实现」/「决定不做」并写理由 |
| 代码有、设计没有 | 补进设计（或行为说明） |
| 设计与代码不一致 | 裁决后改另一边 |
| 用例与设计、代码不一致 | 改用例 |
| 代码缺陷 | 修代码，同时在用例的「历史缺陷回归点」加一条 |

对齐完一个功能域，**实跑一遍它的用例**，以实际结果修正预期、填写追踪表，这个域才算统一。

**执行顺序（2026-10-14 负责人决定）**：先把所有功能域的代码、设计与用例改完（每个域做到单元 / PG 测试通过并提交），**最后统一部署、统一跑一轮回归**，按实际结果修正预期、填追踪表；不在每个域做完后单独部署实跑。

### 3.3 建立可追溯的连接

- 追踪表加一列「设计依据」，写到章节（如 `shared-storage-design §9.5`、`行为说明-虚拟机 §3`）；没有依据的写「代码：`<文件>`，无设计」，回顾时一眼看出哪些预期只是照代码写的。
- 每条用例开头写「依据：…」，与追踪表一致。
- 设计文档的验收 / 测试章节反过来引用用例编号（共享存储设计已经这样做）。
- **2026-10-14 已实现**：追踪表「设计依据」列与写法见 `test-items/README.md`「回归功能追踪表」；被引用的设计文档末尾有生成的「回归用例对照」表（章节 → 功能 → 用例），覆盖检查脚本校验引用都存在、对照表与追踪表一致。第一个落地的是 `cpgateway-go-migration-plan.md` §14。

用例预期的写法约定：

- 有设计依据的：按设计写预期，代码不符就记失败。
- 没有设计依据、明显不合理的行为（越权、数据丢失、注入）：写「应当」的预期，并注明「按代码会失败」。
- 没有设计依据、拿不准意图的：写「记下实际行为」，不预设对错，回顾时补裁决。

### 3.4 防止再分开

1. **改动规则**（写进 `CLAUDE.md`）：改变行为的代码改动，在同一批提交里同时改设计（或行为说明）、用例、追踪表；修 bug 加回归点。提交回顾时按这条检查。
2. **覆盖检查脚本进 CI**：从 `api/src/apis/routes.go` 与 `cpgateway/src/apis/proxy_routes.go` 列出全部对外接口，检查每个接口至少被一条用例或追踪表的一行引用；新增接口没有用例，CI 报出来。
3. **发版回归**：每次发版在追踪表最右边加一列「测试结果（<版本> <提交> <日期>）」（<提交> 是填结果所依据的构建，规则见 `test-items/README.md`），按用例重跑后填写；结果是「失败」「未测」的，必须对应一个处理（缺陷编号、环境限制、决定不做），不能留空。
