# 中转网关

中转网关（Transit Gateway）把同一组织、同一区域里的多个 VPC 接到一起，让它们的云服务器用内网地址互访。默认全部互通；也可以用多张路由表做隔离（例如中心辐射：各业务 VPC 只能访问公共服务 VPC，彼此不通），按网段决定传播哪些子网，或者加静态路由与黑洞。

设计与实现细节见 [VPC 互联：分布式 Transit Gateway](../architecture/plan/vpc-transit-gateway-plan.md)。

---

## 工作方式

- **分布式，没有集中节点**：流量在源云服务器所在的计算节点上直接转进目标 VPC，再经 VXLAN 送到目标云服务器所在的节点。中转网关本身不是瓶颈，一台计算节点出故障只影响它上面的云服务器。
- **不做地址转换**：对方看到的源地址就是本方云服务器的内网地址，安全组可以直接按对方 VPC 的网段放行。
- **不限速**：VPC 之间的流量与 VPC 内跨子网的流量一样，不受「没有浮动 IP 的云服务器出公网」那条限速的影响。

## 概念

| 对象 | 说明 |
|---|---|
| **中转网关** | 一组互联的 VPC 的容器，创建时自带一张名为 `default` 的路由表 |
| **挂载** | 一个 VPC 接入中转网关。每个挂载**关联**一张路由表：这个 VPC 发往中转网关的流量按这张表转发 |
| **路由表** | 一组「目的网段 → 挂载」的路由。不同挂载关联不同的表，就能做隔离 |
| **传播** | 把某个挂载的 VPC 的子网自动写进某张路由表；可以只传播其中一部分网段（前缀列表） |
| **静态路由** | 手工写的「网段 → 挂载」或「网段 → 黑洞（丢弃）」，同一网段时优先于传播来的路由 |
| **有效路由** | 一张路由表最终生效的路由（传播 + 静态 + 黑洞），与计算节点上实际装的一致 |

## 限制

- 只能挂**本组织**的 VPC（系统管理员也不能跨组织挂载）；一个 VPC 只能挂一个中转网关。
- 每个中转网关最多 10 个挂载、20 张路由表，每张表最多 100 条静态路由。
- 成员 VPC 的子网**不能互相重叠**，也不能与下面这些网段重叠：
  - `192.168.196.0/24`：每个 VPC 给负载均衡与 VPN 网关保留的 VRRP 子网
  - `169.254.254.0/24`：中转网关内部的连接地址
  - 其他成员 VPC 的 VPN 网关的对端网段、客户端地址池
- **不做 VPN 中转**：从 VPN 网关进来的流量不会转到其他成员 VPC，反过来也一样。同一个 VPC 同时有 VPN 网关和中转网关挂载是可以的；VPN 隧道的 BGP 地址不能用 `169.254.254.0/24`。
- 负载均衡的后端不能放在别的 VPC。
- 公网子网、经典 VLAN 子网不参与。
- 删除还挂着的 VPC、或还有挂载的中转网关，会被拒绝（409）：先解绑。

## 快速开始（全互通）

1. **创建中转网关**：网络 → 中转网关 → 创建，填名称。
2. **挂载 VPC**：在中转网关详情的「挂载」标签页点「挂载 VPC」，选择 VPC，路由表保持 `default`，勾选「传播到默认路由表」。对每个要互通的 VPC 重复一次。
3. **等状态变为「可用」**：平台把配置下发到所有相关的计算节点，各节点应用后挂载才变为可用，通常几秒。
4. **放行安全组**（见下一节）。

挂上之后，各 VPC 的云服务器直接用对方的内网地址访问，不需要改云服务器里的路由。

## 安全组

VPC 的默认安全组放行任意来源的 ICMP、22（SSH）、3389（RDP），**TCP/UDP 的其他端口只放行本 VPC 自己的子网**。所以挂上中转网关后：

- ping 和 SSH 马上就能通；
- 其他端口（例如 Web 服务的 8080）不通，要在**目标云服务器**的安全组里加一条入站规则，源网段写对方 VPC 的子网。

::: tip 用 TCP 判断是否打通
ping 能通只说明路由通了，不说明安全组放行了你的业务端口。
:::

## 路由表与隔离（中心辐射示例）

场景：`shared` VPC 放公共服务，`app-a`、`app-b` 两个业务 VPC 都要访问 `shared`，但彼此不能互访。

1. 先按快速开始把三个 VPC 都挂上（都关联 `default`，都传播进 `default`）。
2. 在「路由表」标签页新建路由表 `spokes`。
3. 把 `app-a`、`app-b` 的挂载改为关联 `spokes`（挂载列表 → 修改路由表）。
4. 在 `spokes` 里添加传播：只添加 `shared` 的挂载。
5. 在 `default` 里删除 `shared` 自己的传播（可选，`shared` 关联的是 `default`，它自己的网段写在里面没有作用）。

结果：

| 源 | 关联的表 | 表里有 | 能访问 |
|---|---|---|---|
| `shared` | `default` | `app-a`、`app-b` | 两个业务 VPC |
| `app-a` | `spokes` | `shared` | 只有 `shared` |
| `app-b` | `spokes` | `shared` | 只有 `shared` |

`app-a` 访问 `app-b` 的包在 `app-a` 自己的路由器里就被丢弃，不会经公网绕出去。

::: warning 两个方向都要有路由
A 能到 B、B 到不了 A 时，回包会被丢弃，连接建不起来。配置隔离时确认两边的关联表里都有对方。平台不阻止这种配置（单向的黑洞有时是有意的），但会在中转网关详情页顶部用黄色提示列出所有「A 能到达 B、B 没有回到 A 的路由」的 VPC 对。
:::

## 只传播部分网段

添加传播时可以填前缀列表（每个前缀必须与该 VPC 的某个子网重叠）：

- 不填：传播这个 VPC 的所有子网，**以后新建的子网也自动传播**。
- 填了：只传播子网落在列表里的部分（例如子网是 `10.2.0.0/16`、列表写 `10.2.1.0/24`，只传播 `10.2.1.0/24`）；以后新建的子网按同一份列表判断。

没传播进表的成员网段，在关联这张表的 VPC 里会被丢弃。

## 静态路由与黑洞

- **静态路由**：把一个网段指向某个挂载，同一网段时优先于传播来的路由；不同网段按最长前缀匹配。
- **黑洞**：丢弃发往这个网段的流量，可以用来在已传播的子网里屏蔽一段地址；再加一条更具体的静态路由，就能在黑洞里放行一部分。
- 不能写默认路由 `0.0.0.0/0`（会把 VPC 出公网的流量也引进中转网关），不能与 `169.0.0.0/8` 重叠，也不能与成员 VPN 网关的网段重叠。
- 不管路由表里写了什么，**每个 VPC 自己的子网始终留在 VPC 内部**：一条覆盖面很大的路由（例如 `10.0.0.0/8`）不会把 VPC 内部的流量引走。

「有效路由」标签页按路由表列出最终生效的路由和来源（传播 / 静态 / 黑洞），与计算节点上实际装的一致，排查时先看这里。

## 状态

挂载：

| 状态 | 含义 |
|---|---|
| 挂载中 | 平台已下发，等相关计算节点全部应用 |
| 可用 | 所有相关节点都已应用 |
| 解绑中 | 等相关节点都删除这个 VPC 的配置，完成后挂载消失；解绑失败时保持此状态并显示原因，再点一次「解绑」重试 |
| 错误 | 有节点应用失败，或 5 分钟内没有回报（原因里列出节点）；节点恢复后平台会自动重发，各节点都应用后回到「可用」 |

中转网关详情的「同步状态」：已同步（所有节点都应用了最新改动）、同步中、错误。节点列表里每台节点的状态：

| 状态 | 含义 |
|---|---|
| 已同步 | 应用了最新改动 |
| 等待中 | 还没应用最新改动 |
| 出错 | 应用失败，原因列在后面 |
| 退出中 | 这台节点上已经没有成员 VPC 的云服务器，正在删除它上面的中转配置，删完后从列表里消失 |

没应用成功的节点（包括下发时离线、之后又回来的节点），平台每隔一段时间自动重发一次（1 分钟起，逐次加倍，最长 10 分钟）。「重新下发」立即把当前配置重新发给所有节点，节点上已经一致的部分不会变动。

## 常见问题

- **挂上了，ping 通但业务端口不通**：安全组，见上文。
- **一直是「挂载中」**：有计算节点没回报。系统管理员在中转网关详情里能看到每台节点的状态；5 分钟后挂载会变为「错误」并列出节点。
- **带浮动 IP 的云服务器**：访问其他 VPC 走中转网关，出公网仍走浮动 IP。
- **迁移云服务器**：迁移期间跨 VPC 访问的中断与同 VPC 内一样（通常 1 秒以内），迁到原本没有成员的节点也一样。
- **计算节点上多出了别的 VPC 的路由器**：正常。相关计算节点上会有所有成员 VPC 的路由器，用来在本地完成转发；解绑或节点上不再有成员云服务器时会自动回收。
