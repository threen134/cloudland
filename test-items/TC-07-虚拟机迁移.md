# TC-07 虚拟机迁移（MIG）

优先级 **P0** · 会真实搬动虚拟机与磁盘 · 约 30 min

> 🚫 **只用一次性虚拟机测试，绝不迁移 `rb-be*`。** 迁移中断会影响 `rb-lb` 的健康状态。

## 设计约定（判定预期的依据）

### 流程

```
POST /migrations
  → 目标节点 target_migration.sh        (target_prepared)
  → 源节点   source_migration.sh        (source_prepared)
  → 目标节点 complete_migration.sh      (completed，回传 vm_state=)
  → 源节点   finish_source_migration.sh (清理)
```

失败走：`source_rollback` → 目标 `clear_target_migration.sh` → 源 `rollback_source_migration.sh`。

失败态汇总为 `failed` 的有：`source_rollback` / `not_supported` / `timeout` / `failed`。

### 本地存储的限制

本地存储（2026-09-22 起唯一的存储方式，WDS 已删除）：

- **只支持源节点在线时迁移**
- 运行中：`virsh migrate --live --copy-storage-all --migrate-disks`（目标节点按迁移计划预建同虚拟大小、同簇大小的空 qcow2）
- 关机时：先 `rsync -S` 复制磁盘（保持稀疏）再 `--offline`
- 目标上已存在同名磁盘文件则**中止**
- 目标机器的磁盘检查与预建由源端经 ssh 做（`prepare_migration_disks.sh`，带 `pool_guard` 与按实际数据量的空间预检）
- 完成后删除源节点磁盘文件

### ⭐ `force` 不是「冷迁移」开关

`force` 是「**源节点已离线时强行迁移**」（需要共享存储）。

- 热 / 冷由后端自行判定：源节点在线即 `warm`
- 虚拟机是开机还是关机，决定脚本用 `--live` 还是 `--offline`
- **用户无从选择**

本地存储 + `force=true` → **API 直接 400**，报错是 `Force migration is not supported with local storage`。

```bash

 "keys":[{"id":"$K"}],"primary_interface":{"subnets":[{"id":"$S"}]}}
```

## MIG-04 迁移进度上报

**P1**

`source_migration.sh` 后台每 3 秒取 `virsh domjobinfo --rawstats`（`data_processed` / `data_total`，含内存与本地磁盘），经回调 `migrate_progress.sh` 写入 `migrations.progress` / `transferred` / `total`。

- [ ] 迁移中详情页每 3 秒刷新，进度条推进
- [ ] 列表页每 5 秒刷新，进度列更新
- [ ] **百分比单调不回退**
  > libvirt 先只统计磁盘镜像，开始传内存后 `data_total` 变大，原始百分比会掉。clapi 侧做了单调处理。
- [ ] `virsh migrate` 返回即停止上报，completed 时 clapi 置 100
- [ ] `GET /migrations` 与 `GET /migrations/:id` 都返回 `progress` / `transferred` / `total`
- [ ] `phases` 里带 `message`（失败原因）

### 界面字段

- [ ] 列表页读的是 `instance{}` / `source_hyper` / `target_hyper` / `type`
  > **回归点**：前端曾读 `instance_id` / `source_node` / `dest_node` / `migration_type`，`m.instance_id.slice()` 直接抛错；创建迁移发的也是旧字段。2026-09-15 修正，同时给 `GET /hypers` 补了 `hostid`（创建迁移要用它做 `target_hyper`）。

## MIG-05 网络切换时的中断时长

**P1** — 需要在迁移期间持续打流量

```bash
# 在迁移开始前起，间隔 0.1 秒
ssh work-01 'ping -i 0.1 -w 120 <虚拟机浮动IP> | tail -3'
```

### 实测基线（work-01 → work-03）

| 场景 | 中断 |
|---|---|
| 公网子网 | 0.5–0.6 秒 |
| VPC 内部互访 | 约 0.6 秒（= 虚拟机停机时间） |
| 浮动 IP 切换时 | 约 0.6 秒 |
| completed 阶段（浮动 IP / 出外网） | 再断约 1.1 秒 |
| completed 时 reapply_secgroup 先清后建 | 约 0.2 秒空窗 |

- [ ] 各场景中断时长在上表量级内（不要求精确，量级差一个数量级就要查）
- [ ] 迁入**已有同 VPC 虚拟机**的节点，不出现约 1 分钟的断网

### completed 阶段的 1.1 秒：**决定不改**（2026-09-15）

只丢包不断连接（TCP 重传可恢复），只影响经路由器的浮动 IP / 出外网，内部二层互访不受影响。可选改法都要动 `LaunchVM sync` 这条创建、同步、救援共用的公共流程，收益 1 秒、风险不成比例。

**不要把它当缺陷报。**

## MIG-06 回滚

**P1**

构造「目标上已存在同名磁盘文件」来触发失败：

```bash
# 在目标节点上预先建一个同名文件
ssh work-0X 'touch /opt/cloudland/cache/instance/instance-<N>.disk'
```

然后发起迁移。

- [ ] 迁移中止，任务状态 `failed`
- [ ] 目标节点上**预建的磁盘被删除**（否则重试永远卡在「目标已存在同名磁盘」）
- [ ] 目标节点的安全组链、VPC 路由器被清理（`clear_target_migration.sh` 按 clapi 传入的路由器 ID 和网卡 MAC 清）
- [ ] 源节点上虚拟机**重新启动后不会被销毁**
  > **回归点**：`finish_source_migration.sh` 的「源节点是否还有该虚拟机」判断原先在 destroy/undefine **之后**，回滚后重新启动的虚拟机会被销毁并删掉唯一的磁盘。
- [ ] 回调 handler **不 panic**
  > **回归点**：`target_prepared` 分支里源节点失败后，冷迁移会调 `LaunchVM` 并把返回值赋给同一个 `err`，成功时 `err` 变 nil，随后仍执行 `err.Error()` → 空指针 panic。现在先把原始失败原因存入 `migrateErr`。

## MIG-07 调度器自选目标节点

**P0**

不指定 `target_hyper` 发起迁移。

- [ ] 迁移能走到 `completed`，**不卡在 `source_prepared` 99%**

### 缺陷背景（表现极具迷惑性）

创建迁移不指定目标时 `target_hyper` 存 **-1**，实际节点只有 `target_prepared` 回调知道。但 `migrate_vm.go` 原先只在**内存里**给 `migration.TargetHyper` 赋值（defer 落库只写 `status`），于是 `complete_migration.sh`、`clear_target_migration.sh` 都以 `inter=-1` 下发、被 cland 丢弃。

**表现**：虚拟机已在目标节点正常运行、数据完整，两个阶段任务都是 completed、无任何报错，只有迁移记录停在 `source_prepared` 99%、实例卡在 `migrating`。

修法：回调里把 `target_hyper` 落库。

### 卡死后不会自愈

`report_rc.sh` 只上报相对 `old_inst_list` **有变化**的虚拟机。虚拟机在目标节点持续 running 时 `old_inst_list` 已记录该状态，不会再触发 `inst_status` 回调 —— 即使过了 10 分钟活跃迁移宽限期也等不到自愈，**必须手工恢复**（实例 status/hyper、`volumes.hyper`、源节点残留磁盘）。

`inst_status` 只修 `instances` 与 `interfaces` 的 hyper，**不修 `volumes.hyper`**。

- [ ] 迁移完成后 `volumes.hyper` 也跟着更新了
  ```bash
  ssh work-01 'docker exec cloudland-postgres psql -U postgres -d cloudland -t -c \
    "select v.name, v.hyper, i.hostname, i.hyper from volumes v join instances i on v.instance_id=i.id where i.hostname=\"wp-mig\";"'
  ```

## MIG-10 存储池与迁移计划（2026-09-22 起）

**P1** — 详细用例见 [`TC-16-本地存储池.md`](TC-16-本地存储池.md) 的 STO-04，这里只列迁移侧必查的

磁盘默认**留在原池**；可以逐盘换池（请求体 `disks`），目标没有原池时只在同一个 `fallback_group` 内自动替换（`allow_pool_fallback`，默认 true）。计划在指定目标时创建即生成、不指定时在 `target_prepared` 回调里生成。

- [ ] `GET /instances/:id/migration_targets` 列出候选机器与每块盘可选的池
- [ ] 不指定目标时，调度只在「每块盘都能保留原池」的机器里选
- [ ] `GET /migrations{,/:id}` 返回 `disk_plan`，详情页显示逐盘的源池 → 目标池
- [ ] 迁移中 `storage_reservations` 有该迁移的预留，**结束后清零**
  > ⚠️ 失败路径要特别确认：`reservations` 里不该留下已结束迁移的行（挂着会挡住目标机器的新分配和删池）
- [ ] 目标池放不下时**复制前**就失败并回滚，目标池无残留、可以重试
- [ ] **关机换池迁移**后，目标上的域定义指向新路径
  > **回归点**：libvirt 12 的 `virsh migrate --offline` **忽略 `--persistent-xml`**，目标曾定义成源端旧路径、虚拟机起不来。现在由源端 ssh 到目标 `virsh define` 改写后的 XML
- [ ] 关机迁移后目标文件保持**稀疏**（`du` 与源端一致）
- [ ] 带数据卷迁移后，卷记录的**池和路径**都更新（不只是 `hyper`）

## 已知现象（不是缺陷）

| 现象 | 说明 |
|---|---|
| 复制磁盘期间出现 SLOW SQL（>200ms），`hypers` 等无关表也变慢 | 本地 I/O 打满，postgres 与迁移在同一节点。不是进度更新本身的问题 |
| 异步任务（`async_exec`）的输出要等下次心跳（1–20 秒）才转发给 clapi | 热迁移的 `complete_migration.sh` 在目标域已持久定义时同步执行以立即回调 |
| 节点宕机后无法直接重新部署，必须先 `DELETE /hypers/<uuid>` 再注册 | **产品待改进**，不是回归缺陷。`HyperAdmin.Deploy` 只在 status 4/5 允许重试 |
