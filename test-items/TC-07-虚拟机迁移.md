# TC-07 虚拟机迁移（MIG）

优先级 **P0** · 会真实搬动虚拟机与磁盘 · 约 45 min（MIG-11 另约 10 min，MIG-12 要停 cland-go）

> 🚫 **只用一次性虚拟机测试，绝不迁移 `rb-be*`，也不迁移其他保留虚拟机**（`big-vm`、`net-a/b/c`、VPN 的 `ix*`、`ir*`、`ax*`）。迁移中断会影响 `rb-lb` 的健康状态和 VPN 保留环境。

## 设计约定（判定预期的依据）

### 流程

```
POST /migrations
  → 目标节点 target_migration.sh        (target_prepared)
  → 源节点   source_migration.sh        (source_prepared)
  → 目标节点 complete_migration.sh      (completed，回传 vm_state=)
  → 源节点   finish_source_migration.sh (清理)
```

失败走：`source_rollback` → 目标 `clear_target_migration.sh` → 回调 `rollback` → 源 `rollback_source_migration.sh`。

- 阶段任务：`Prepare_Target`（创建时建）、`Prepare_Source`（`target_prepared` 回调里建）、`Source_Rollback`（回滚时建）。
- 迁移状态为 `failed` / `not_supported` / `source_rollback` / `rollback` / `timeout` 时，当前阶段任务记为 `failed`，迁移预留随即释放（事务外释放）。
- 迁移记录停在 `rollback` 是**终态**（回滚做完了），不是「还在回滚」。
- cland 拒绝（`error=resource`）时回传的是 `target_migration.sh`，由 `TargetMigrationRefused` 处理（MIG-11），不是 `migrate_vm.sh`。

### 本地存储的限制

本地存储（2026-09-22 起唯一的存储方式，WDS 已删除）：

- **只支持源节点在线时迁移**
- 运行中：`virsh migrate --live --copy-storage-all --migrate-disks`（目标节点按迁移计划预建同虚拟大小、同簇大小的空 qcow2）
- 关机时：先 `rsync -S` 复制磁盘（保持稀疏）再 `--offline`；换池时 `--offline` 忽略 `--persistent-xml`，由源端 ssh 到目标 `virsh define` 改写后的 XML
- 目标上已存在同名磁盘文件则**中止**
- 目标机器的磁盘检查与预建由源端经 ssh 做（`prepare_migration_disks.sh`，带 `pool_guard` 与按实际数据量的空间预检）；它把自己建的文件记在目标的 `/opt/cloudland/run/migration-<迁移 ID>.created`，回滚只删这些
- 完成后删除源节点磁盘文件
- 磁盘路径（`volumes.path` 相对池根）：内置池系统盘 `instance/inst-<实例 ID>.disk`、内置池数据盘 `volume/volume-<卷 ID>.disk`（池根 `/opt/cloudland/cache`）；其他池一律 `volumes/volume-<卷 ID>.disk`（池根 `/opt/cloudland/pools/<池 uuid>`）

### ⭐ `force` 不是「冷迁移」开关

`force` 是「**源节点已离线时强行迁移**」（需要共享存储）。

- 热 / 冷由后端自行判定：源节点在线即 `warm`（`createOne` 固定写 `type=warm`，**关机的虚拟机迁移也记 `warm`、列表显示「热迁移」**，这是设计，2026-09-28 记为观察）
- 虚拟机是开机还是关机，决定脚本用 `--live` 还是 `--offline`
- **用户无从选择**

本地存储 + `force=true` → **API 直接 400**，报错是 `Force migration is not supported with local storage`。

- 虚拟机建在临时 VPC `wp-vpc` / 子网 `wp-net` 或现成的 `mig-vpc` / `mig-int` 里，建法见 `TC-02` 的「前置」。

- **公网 IP**：MIG-05 要给 `wp-mig` 绑浮动 IP，占用唯一的空闲地址 `52.117.101.158`，和 `TC-02` VM-06、`TC-04`、`TC-06`、`TC-17` 排队，用完立刻释放。

**P1** — 需要在迁移期间持续打流量；要占用唯一的空闲公网地址（见「执行环境」）

```bash
# 在迁移开始前起，间隔 0.1 秒
ssh work-01 'ping -i 0.1 -w 120 <虚拟机浮动IP> | tail -3'
```

### 实测基线（work-01 → work-03）

| 场景 | 中断 |
|---|---|
| 公网子网 | 0.5–0.6 秒 |
| VPC 内部互访 | 约 0.6 秒（= 虚拟机停机时间） |
| 浮动 IP 切换时 | 约 0.6 秒 |
| completed 阶段（浮动 IP / 出外网） | 再断约 1.1 秒 |
| completed 时 reapply_secgroup 先清后建 | 约 0.2 秒空窗 |

2026-09-28 复测：迁入已有同 VPC 虚拟机的 work-01，浮动 IP 的 ping 最长中断 0.94 秒；虚拟机内每 0.1 秒探测同 VPC 虚拟机的 22 端口只失败一次（约 0.4 秒）。

- [ ] 各场景中断时长在上表量级内（不要求精确，量级差一个数量级就要查）
- [ ] 迁入**已有同 VPC 虚拟机**的节点，不出现约 1 分钟的断网（目标上先放一台同 VPC 的 cirros，如 `wp-cir-2`）

### completed 阶段的 1.1 秒：**决定不改**（2026-09-15）

只丢包不断连接（TCP 重传可恢复），只影响经路由器的浮动 IP / 出外网，内部二层互访不受影响。可选改法都要动 `LaunchVM sync` 这条创建、同步、救援共用的公共流程，收益 1 秒、风险不成比例。

**不要把它当缺陷报。**

## MIG-07 调度器自选目标节点

**P0**

不指定 `target_hyper` 发起迁移。

- [ ] 迁移能走到 `completed`，**不卡在 `source_prepared` 99%**
- [ ] 创建响应里 `target_hyper` 是 **-1**（界面显示「自动选择」）；`target_prepared` 回调之后库里是真实 hostid（放置组成员例外：创建时就写好，见 `TC-18` PG-23）
- [ ] 目标只在「每块盘都能留在原池」的节点里选（g1），都不行才考虑换池的（g2）

### 缺陷背景（表现极具迷惑性）

创建迁移不指定目标时 `target_hyper` 存 **-1**，实际节点只有 `target_prepared` 回调知道。但 `migrate_vm.go` 原先只在**内存里**给 `migration.TargetHyper` 赋值（defer 落库只写 `status`），于是 `complete_migration.sh`、`clear_target_migration.sh` 都以 `inter=-1` 下发、被 cland 丢弃。

**表现**：虚拟机已在目标节点正常运行、数据完整，两个阶段任务都是 completed、无任何报错，只有迁移记录停在 `source_prepared` 99%、实例卡在 `migrating`。

修法：回调里把 `target_hyper` 落库。

### 卡死后不会自愈

`report_rc.sh` 只上报相对 `old_inst_list` **有变化**的虚拟机。虚拟机在目标节点持续 running 时 `old_inst_list` 已记录该状态，不会再触发 `inst_status` 回调 —— 即使过了 10 分钟活跃迁移宽限期也等不到自愈，**必须手工恢复**（实例 status/hyper、`volumes.hyper`、源节点残留磁盘）。

`inst_status` 只修 `instances` 与 `interfaces` 的 hyper，**不修 `volumes.hyper`**。

- [ ] 迁移完成后 `volumes.hyper` 也跟着更新了（completed 回调按 `disk_plan` 同时改卷的 `hyper`、`storage_pool_id`、`path`）
  ```bash
  ssh work-01 'docker exec cloudland-postgres psql -U postgres -d cloudland -t -c \
    "select v.name, v.hyper, v.storage_pool_id, v.path, i.hostname, i.hyper from volumes v join instances i on v.instance_id = i.id where i.hostname = '"'"'wp-mig'"'"' and i.deleted_at is null;"'
  ```
