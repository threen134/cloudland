优先级 **P1** · DEP 用例要重装或新增机器（**要用户同意**），HYP 用例会迁走、停用、删除计算节点 · 约 135 min（不含重装）

2026-10-14 按代码与部署文档核对后新建。此前一键部署、计算节点注册与部署、控制面 HA、多区域、计算节点的维护与删除都**没有任何用例**，只在 CLAUDE.md 的部署记录里留下过实际做过的结果。依据：`docs/architecture/plan/operations-behavior.md` §1、§4、§5、§6（2026-10-14 功能域对齐 04 补的行为说明），部署步骤以 `docs/deployment/02`–`05` 为准。内部 DNS（控制面 dnsmasq）的依据是 `docs/architecture/plan/internal-dns-plan.md`（2026-10-15 按代码重写，同日补 DEP-07，未执行）。

## 设计约定（判定预期的依据）

- **控制面**：以 root 执行 `deploy-control-node.sh`（`sudo -i` 后 export 变量）；`COMPOSE_PROFILES` 组合 `full` / `dev` / `region` / `minio`；`REPO_BRANCH` 优先级：显式环境变量 > `.env` > 已有仓库的当前分支 > `staging`；密码与密钥为空时脚本生成（`GRPC_AUTH_TOKEN`、`CAPTURE_UPLOAD_SECRET`、`VPN_SECRET_KEY`、`ALERT_WEBHOOK_TOKEN` 等）；`MANAGEMENT_VIP` 必须是内网地址；遥测端口与 5006 绑 `TELEMETRY_LISTEN_IP` / `GRPC_LISTEN`，单控制节点没显式设置且 `MANAGEMENT_VIP` 等于 `INTERNAL_IP` 时脚本设为这个地址（2026-10-14 对齐 04 O10）；所有部署脚本写 apt 配置 `DPkg::Lock::Timeout "600"`（O9）
- **计算节点**：`POST /hypers {ip, hostname, network_device, vlan_device, private_vlan_device, dns_server, domain, zone_name, virt_type}` 建 hyper（状态 4 deploying）并返回 `deploy_command`；节点上执行它：编译 cloudlet-go、写 `/etc/sysconfig/cloudlet`（`NODE_ID`、`CLAND_ENDPOINT`、`GRPC_AUTH_TOKEN`）、`cloudlet-go node-add` 取回 cland SSH 密钥对、装依赖（libvirt、haproxy、keepalived、socat、strongSwan、WireGuard、FRR……并禁用它们的系统服务）、sudo-rs 换回经典 sudo、bond 切到 NetworkManager（`switch_bond_to_nm.sh`）、装 `cloudland-iptables.service`；cloudlet 注册成功后状态变为 1
- **重新部署**：`HyperAdmin.Deploy` 只在状态 4 / 5 时允许重试；离线（10）的节点要先删除再注册（待办 B4）
- **计算节点状态**：0 停用、1 可用、2 维护、4 部署中、5 部署失败、10 离线；启用 / 停用按当前状态处理：4 / 5 拒绝，10 只记 `offline_prior`（O8）
- **维护**：`POST /hypers/:uuid/maintain {migrate, target_hyper}` 只对状态 0 / 1；有迁入中的迁移时拒绝；置状态 2，`migrate` 时把节点上的云服务器批量迁走（每台独立，迁不走的记在结果里）
- **删除**：还有云服务器、还在存储集群里、还有隔离记录时拒绝；`keep_pools` 决定本地存储池的记录保留与否（`TC-16` STO-08）
- **内部 DNS**（`internal-dns-plan.md` §3–§6）：控制面 dnsmasq（`cloudland-dnsmasq`，只监听 `INTERNAL_IP:53`）解析计算节点主机名、控制节点主机名、`MINIO_HOSTNAME` / `CLAPI_HOSTNAME`，其余转发上游。`deploy/dns/hosts/` 下一个文件一个写入方：`hyper-hosts` 归 clapi（注册、删除、心跳报的主机名或地址变了之后按 `hypers` 表重写那个名字的行，心跳在事务提交之后才写；同名的多台节点指向 `hostid` 最小的那台；每次启动整份重建，内置 MinIO 的名字与 `CLAPI_HOSTNAME` 指 `MANAGEMENT_VIP`、和节点一次写入），`control-hosts` 归 `deploy-control-node.sh`（`INTERNAL_IP 控制节点主机名`），文件都是 644、dnsmasq 以非 root 用户读。上游在 `conf.d/upstream.conf`（每个地址一行 `server=`），由 clapi 按系统设置 `DNS_UPSTREAM` 写、在 dnsmasq 容器里 `kill -HUP 1` 重载。计算节点 resolv.conf 的**第一个** nameserver 是 `CONTROLLER_IP`（= `MANAGEMENT_VIP`），后面还有网卡自己带的解析器（IBM Classic 节点是 bond1 的 `10.0.80.11`、`.12`）；`DNS_SERVER` 只写进 `cloudrc.local` 的 `dns_server`，是给虚拟机用的

## DEP-01 一键部署控制节点（要用户同意，重装或新机器）

1. 在一台干净的 Ubuntu 24.04 上按 `docs/deployment/02-quick-start.md` 部署，`COMPOSE_PROFILES=full,dev,region,minio`，不给密码与密钥
2. 另一次给 `REPO_BRANCH=stage-01`；再一次不给、`.env` 里有；再一次都不给、已有仓库检出在 `stage-01`
3. 部署时 unattended-upgrades 正占着 dpkg 锁（新装系统开机后常见）

**预期**：
- 第 1 步：全部容器健康，`https://<公网>` 能登录，`.env` 里生成了各项密钥（含 `ALERT_WEBHOOK_TOKEN`，`cloudland-alertmanager` 的 `/tmp/webhook_token` 与它一致）；外网只开 80 / 443（`TC-13` SEC-04 的扫描）；没给 `TELEMETRY_LISTEN_IP` / `GRPC_LISTEN` 且 `MANAGEMENT_VIP` 等于 `INTERNAL_IP` 时 `.env` 里是这个地址，`ss -ltn` 看 5006、3100、4317 只在这个地址上，cland-go 的链路照常进 Tempo；两者不同时仍监听全部地址、部署日志有提示（2026-10-14 对齐 04 O10；按代码会失败（改动之前）：原先默认监听全部地址，loki 与 OTLP 无鉴权）；MinIO 用 `cgr.dev/chainguard/minio`（官方镜像已拉不到）；`deploy/dns/hosts/` 下有 `hyper-hosts` 与 `control-hosts`（后者一行 `INTERNAL_IP 本机主机名`），`deploy/dns/conf.d/upstream.conf` 按 `.env` 的 `DNS_UPSTREAM` 每个地址一行 `server=`（细节见 DEP-07）。
- 第 2 步：clapi 容器与 `deploy_command` 里的分支按优先级取。
- 第 3 步：脚本等锁（最多 10 分钟）后继续，不再 exit 100；`/etc/apt/apt.conf.d/90cloudland-lock-timeout` 存在。三个部署脚本都这样（2026-10-14 对齐 04 O9 修；原先 apt 不等锁直接失败，等锁释放后重跑才成功）。

## DEP-02 注册并部署计算节点（要用户同意）

1. 界面「计算节点 → 注册」（或 `POST /hypers`），填内网 IP、主机名、三个网络设备、可用区
2. 在节点上执行返回的 `deploy_command`（`systemd-run --setenv=HOME=/root` 后台跑）
3. 部署完看节点详情、`/etc/sysconfig/cloudlet`、`sudo --version`、`nmcli connection`、`systemctl is-enabled cloudland-iptables`、`ip -d link show v-<vni>` 的 dstport
4. 在新节点上建一台云服务器，和其他节点的同 VPC 云服务器互通

**预期**：
- 第 1 步：200，状态 4，返回的命令里带 `CONTROLLER_IP`（= `MANAGEMENT_VIP`，内网）、分支、令牌；控制节点的 `deploy/dns/hosts/hyper-hosts` 里马上有 `<填的 IP> <主机名>`（状态 4 就写，不等部署完）。
- 第 2 步：脚本跑完 cloudlet 注册，状态变 1；`hostid` 是新分配的。
- 第 3 步：经典 sudo；bond 是 `bond*-nm` 连接、`90-NM-*.yaml` 都在；`cloudland-iptables` enabled；VXLAN dstport 8472；VPN、LB、控制台、存储预检要的依赖都装了且系统服务禁用；resolv.conf 第一条是 `nameserver <CONTROLLER_IP>`，后面是网卡带的解析器（IBM Classic 节点是 `10.0.80.11`、`.12`；有 systemd-resolved 时 `/etc/resolv.conf` 链到 `/run/systemd/resolve/resolv.conf`，`/etc/systemd/resolved.conf.d/cloudland.conf` 存在），`cloudrc.local` 的 `dns_server` 是注册时填的 `dns_server`，`/etc/hosts` 只有本机一行（别的节点靠 DNS，DEP-07 第 2 步）。
- 第 4 步：跨节点互通（VXLAN 上联口在网桥里且 UP，见 `create_link.sh` 的 2026-10-05 修复）。

## DEP-03 部署失败与重新部署

1. 部署命令中途失败（例如 DEP-01 第 3 步的 apt 锁），节点状态 5；在界面重新取命令再跑
2. 一台可用的节点关机 10 分钟以上（状态 10），想重新部署
3. 删除它再用同一 IP 注册、部署

**预期**：
- 第 1 步：状态 4 / 5 时可以重试，重跑成功后变 1。
- 第 2 步：400（只有 4 / 5 能重新部署，B4）。
- 第 3 步：分到新的 hostid（旧号作废）；节点上旧的 cloudlet 配置被覆盖。⚠️ 有云服务器、存储集群成员身份、隔离记录时删除被拒（HYP-04）。2026-10-10 work-04 就是这样删掉重注册成 hostid 5 的。

## DEP-04 控制面 HA（要两台控制节点，要用户同意）

1. 按 `docs/deployment/03-ha-deployment.md` 部署 MASTER 与 BACKUP，`MANAGEMENT_VIP` 为浮动的内网 VIP
2. 停掉 MASTER 的 keepalived（或关机）
3. 恢复后手工回切

**预期**：
- 第 1 步：BACKUP 从 MASTER 同步 `GRPC_AUTH_TOKEN`、`CAPTURE_UPLOAD_SECRET`、`VPN_SECRET_KEY`、`ALERT_WEBHOOK_TOKEN`（两台签发 / 校验要一致）；VIP 在 MASTER 上。遥测端口仍监听全部地址（要监听 VIP，见 `operations-behavior.md` §4.2）。
- 第 1 步，计算节点的 DNS：在计算节点上 `getent ahostsv4 <另一台计算节点>`、`getent ahostsv4 images.cloudland.internal`、`getent ahostsv4 www.ibm.com` 都能解析。**按代码会失败（未修，`internal-dns-plan.md` §9）**：dnsmasq 只监听各自的 `INTERNAL_IP`，计算节点的第一个 nameserver 是 VIP，VIP 的 53 端口没有进程，glibc 换到后面的解析器：前两个（节点主机名、内部域名）解析不到，`www.ibm.com` 能解析（IBM Classic 节点有 bond1 带来的解析器；没有的环境三个都解析不了）；`deploy-ha-node.sh` 也不建 `deploy/dns/` 目录、不写 `control-hosts` 与初始 `upstream.conf`。前两个先记 FAIL。
- 第 2 步：VIP 漂到 BACKUP，cloudlet 重连到 BACKUP 的 cland，界面与接口照常；切换期间正在下发的命令可能失败一次。
- 第 3 步：按文档「手动 VIP 回切」恢复。
- 后台循环（存储任务、健康看护、告警映射对账）只在拿到 advisory lock 的那台 clapi 上跑（`TC-20` SHS-20 第 8 步）。

## HYP-02 启用 / 停用与属性

1. `PATCH /hypers/<uuid> {"status":0}`（停用）后不指定宿主机建云服务器；再改回 1
2. 改可用区（`zone_id`），看节点 `/etc/sysconfig/cloudlet` 与 cloudlet 是否重启
3. 改超分比例 `cpu_over_rate` / `mem_over_rate` / `disk_over_rate`、备注 `remark`；比例给 0.5
4. 对部署中（4）或部署失败（5）的节点 `PATCH {"status":1}`；对离线（10）的节点 `PATCH {"status":0}`，之后让它回来；再让一台**停用后**离线的节点在离线期间 `PATCH {"status":1}`，之后让它回来

**预期**：
- 第 1 步：停用后调度不再选它（已有云服务器不受影响）；审计 `hyper.disable` / `hyper.enable`。
- 第 2 步：下发 `update_hyper.sh`，改写配置并重启 cloudlet，节点在新可用区里被调度；会触发它上面 LB / VPN 的告警（`TC-06` LB-07b 的注意事项）。
- 第 3 步：下一次心跳后调度用新的比例；小于 1 时 400。
- 第 4 步：4 / 5 时 400（`Hypervisor is deploying` / `deploy_failed`），状态不变、还能重试部署；10 时 200 但状态仍是 10、`offline_prior` 为 0、不下发命令，节点回来后是停用（0），节点上出现 `$run_dir/disabled`、之后上报 state 0、调度不再选它；停用后离线、离线期间启用的那台回来后是可用（1），`disabled` 标记被删掉（2026-10-14 对齐 04 O8；按代码会失败（改动之前）：原先任何状态都直接改，离线节点改成可用后疏散与隔离的判断失效）。

## HYP-03 维护模式

1. 有云服务器的节点 `POST /hypers/<uuid>/maintain {"migrate": true}`（不指定目标）
2. 同上，指定 `target_hyper`
3. 有迁入中的迁移时进入维护；状态是 10（离线）或 2 时进入维护
4. 维护结束后改回可用（`PATCH {"status":1}`）

**预期**：
- 第 1 步：状态变 2，节点上每台云服务器一条迁移（`maintenance-hyper-<id>`），迁不走的在结果里写原因、不影响其他；迁移全部完成后节点上没有运行的云服务器。
- 第 2 步：都迁到指定节点（资源不够的失败）。
- 第 3 步：400「has N incoming migration(s)」/「must be active or disabled to maintain」；调度没有变化。
- 第 4 步：状态回到 1，可以被调度。
- 严格集中放置组的成员整组迁移（`TC-18` PG-10、PG-18）。

## HYP-04 删除计算节点

1. 还有云服务器时删除；还是存储集群成员时删除；还有隔离记录时删除
2. 腾空后删除（`keep_pools` 为 true / false 各一次，用 loop 池）

**预期**：
- 第 1 步：都 400：「Hypervisor still has N instances, cannot delete」「is a member of a storage cluster: remove it from the cluster first」、隔离记录（`TC-24` 回归点 20）。
- 第 2 步：204；cland 下发 Shutdown，cloudlet 正常退出且不被 systemd 拉起；`keep_pools` 的效果见 `TC-16` STO-08；控制节点 `deploy/dns/hosts/hyper-hosts` 里这台的那一行没了，别的节点上 `getent ahostsv4 <它的主机名>` 解析不到（第 1 步被拒时那一行不动）。

## HYP-05 主机监控曲线

1. 节点详情的 CPU、内存曲线（`POST /metrics/hypers/{cpu,memory}/his_data`）
2. 普通成员直接调这两个接口

**预期**：
- 第 1 步：曲线有数据，与 node_exporter 一致（node_exporter 停了时为空）。
- 第 2 步：403 `Only system admins can read host metrics`（网关白名单与 clapi 都限系统管理员）；带查询语法的主机名 400。2026-10-14 修（对齐 02 V3，未部署，部署前照旧记 FAIL）：原先接口不查身份，主机名直接拼进 PromQL，见 `TC-13` SEC-16。依据：`compute-behavior.md` §5.2。

## HYP-06 任务列表

依据：`operations-behavior.md` §6。

1. `GET /tasks`（默认）、`GET /tasks?source=migration`、`GET /tasks?query=<名字片段>`，翻页 `offset` / `limit`
2. `GET /tasks/:id` 取一条本组织的任务；再用外部组织的账号取它

**预期**：
- 第 1 步：只有本组织的任务；默认不含迁移任务，`source=migration` 才列出；负的 `offset` / `limit` 400。
- 第 2 步：本组织 200；外部组织拿到的回答与不存在的任务相同（记下实际状态码）。
