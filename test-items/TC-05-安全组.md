## 设计约定

- **每个安全组创建时都带几条默认规则**（`SecgroupAdmin.Create`，2026-09-28 核对）：出方向 tcp / udp 1-65535 到 `0.0.0.0/0`、入方向 udp 68（DHCP）、icmp 进出任意；带 VPC 的组再加「从该 VPC **当时已有的每个子网**进来的 tcp / udp 1-65535」（含 VRRP 子网）。所以**同一 VPC 内的互访永远放行**，安全组效果要从 VPC 外面（经浮动 IP）测。
- **只有系统自动创建的默认组**（系统默认组、组织默认组、VPC native 组）额外预置对全网开放的 22/3389（`withLoginRules`）。用户经 API 创建的组，**无论 `is_default` 是什么都不预置**。
- 建组权限：带 VPC 要该 VPC 所属组织的写权限；不带 VPC（组织级的组）要组织**管理员**。
- 实例的「登录端口」只改虚拟机内 sshd/RDP 的端口，**不自动放行安全组**。前端留空时后端按镜像类型取 22/3389。
- 规则端口语义（`services/secrule.go`）：
  - tcp / udp：端口范围。API 显式传入必须 1–65535；**两个都不传表示全部端口**（存 1/65535），只传一个表示单端口。
  - icmp：复用 `port_min` / `port_max` 存 **type(0–254) / code(0–255)**，`-1` 表示任意；只给 code 不给 type 400。type / code 可以是 0（零值有业务含义，查询用 map 条件）。
  - gre / ipv6：不区分端口，统一存 -1。
  - 完全相同的规则再 POST 一次：返回**已有**的那条（幂等，200）；PATCH 成与同组另一条完全相同：400。
  - PATCH 不传端口沿用原值；协议在「端口类」与「非端口类」之间切换时，改为 icmp/gre/ipv6 且不传端口取 -1，改为 tcp/udp **必须传端口**。
  - `remote_cidr` 必填且必须是 IPv4 CIDR（后端 `binding:"cidrv4"`，没有 omitempty）。
- VPC 子网上的安全组必须属于该 VPC。
- **下发范围**：规则只下发到用了该组的虚拟机**所在节点**（`sync_nic_info.sh`，`inter=<虚拟机所在节点>`）。节点上：`FORWARD` 里 `-m physdev --physdev-in/out tapXXXX --physdev-is-bridged -j secgroup-chain`（`apply_fw` 插在第 3 条）→ `secgroup-chain` 跳到 `secgroup-in-tapXXXX` / `secgroup-out-tapXXXX`，出方向另有防伪造的 `secgroup-as-tapXXXX`；`secgroup-chain` 最后一条是 `-j ACCEPT`。
- 列表：服务端分页（界面每页 20）+ 名称搜索（`query`，`dbs.Contains` 参数绑定，`%` / `_` 按字面匹配）+ VPC 筛选（`vpc_id`）；`order` 参数被忽略，固定按创建时间倒序，界面各列都不可排序。

## SG-05 规则在节点上真正生效

**P0** · 借用 `TC-04` 挂在 `wp-vm` 上的 `.158`

这是安全组最关键的一条 —— 数据库里有规则不等于流量被拦住。

### 步骤

先把 `wp-vm` 主网卡的安全组换成 `wp-sg-renamed`（它没有 22 端口），再从 VPC 外面（work-01 宿主机或本机）经浮动 IP 探测：

```bash
ssh work-01 'source /root/alarmtest-env.sh
I=$(api GET "/instances?limit=100" | jq -r ".instances[]|select(.hostname==\"wp-vm\")|.id")
IF=$(api GET /instances/$I | jq -r ".interfaces[]|select(.is_primary)|.id")
G=$(api GET "/security_groups?limit=100" | jq -r ".security_groups[]|select(.name==\"wp-sg-renamed\")|.id")
cat > /tmp/ifsg.json <<JEOF
{"security_groups":[{"id":"$G"}]}
JEOF
curl -sk -X PATCH "$B/instances/$I/interfaces/$IF" -H "Authorization: Bearer $T" -H "Content-Type: application/json" -d @/tmp/ifsg.json | jq -c "{security_groups:[.security_groups[]?.name]}"'

# probe from outside the VPC; 124 means timed out (dropped), anything immediate means reachable or refused
ssh work-01 'for p in 22 2222; do timeout 5 bash -c "</dev/tcp/52.117.101.158/$p" 2>/dev/null; echo "port $p exit=$?"; done'
```

在 `wp-vm` 所在节点看链：

```bash
ssh work-0X 'virsh domiflist inst-<N>                     # tap device of wp-vm
iptables -S secgroup-in-<tap>; iptables -S secgroup-out-<tap> | head
iptables -S FORWARD | awk "/-j secgroup-chain/{s=NR} /-i br[0-9]+ -o br[0-9]+ -j ACCEPT/ && !b{b=NR} /REJECT/{r=NR} END{print \"last secgroup-chain=\"s, \"first bridge accept=\"b, \"reject=\"r, \"total=\"NR}"'
```

> `<inst-N>` 的 N 是 `instances.id`：`docker exec cloudland-postgres psql -U postgres -d cloudland -Atc "select id, hyper from instances where hostname='wp-vm' and deleted_at is null"`（`hyper` 就是所在节点的 hostid：1 = work-01，3 = work-03，4 = work-02）。

然后加一条入站 tcp 22（`0.0.0.0/0`）→ 再探测 → 删掉这条 → 再探测。

### 检查项

- [ ] 换组后 `secgroup-in-<tap>` 先清后建，内容与 `wp-sg-renamed` 一致（有 `--dport 80` 那条 `10.0.0.0/8`，没有 22）
- [ ] **只有 `wp-vm` 所在节点**有 `secgroup-in-<tap>` / `secgroup-out-<tap>` / `secgroup-as-<tap>` 链；另外两个节点没有（原写「三个节点都下发」与代码不符，2026-09-28 核对）
- [ ] 访问未放行端口（22、2222）的结果是**超时**（exit=124，被安全组 DROP）
  - 若是**立刻 connection refused**（exit=1），说明安全组被**绕过**了 —— 见下方回归点 1
- [ ] 放行 22 后立刻可连（exit=0），`secgroup-in-<tap>` 里多出 `-p tcp -m tcp -m conntrack --ctstate NEW --dport 22 -j RETURN`
- [ ] 删除这条规则后恢复超时
- [ ] ping `.158` 一直通（`default-ingress-icmp`）

### ⚠️ 回归点 1：FORWARD 链顺序

安全组是否生效取决于 FORWARD 链的顺序：

- 安全组跳转（`-j secgroup-chain`）由 `apply_fw` 插在**第 3 条**
- 网桥内部放行（`-i brX -o brX -j ACCEPT`）**必须排在它之后**

`report_rc.sh` 的 `sync_instance` 曾用 `iptables -I FORWARD 2` 插入，导致**节点重启后，开机时已存在的网桥（如 br756）上所有虚拟机的安全组被完全绕过**。（来自上游 `77e1b809` + `d788855e`，分叉时带入。）

修法：`sync_instance` 与 `apply_bridge` 都改为**追加到链尾**，再把兜底 REJECT 移到最后。

- [ ] 上面 awk 的输出满足 `last secgroup-chain < first bridge accept < reject = total`（所有 `-j secgroup-chain` 跳转都在 `-i brX -o brX -j ACCEPT` **之前**）
- [ ] 兜底 `-j REJECT --reject-with icmp-host-prohibited` 在**最后**

**节点重启后必须重跑这一条**（见 `TC-14`）。三个节点都查一遍 FORWARD 顺序（这一项与有没有测试虚拟机无关）。

## SG-07 规则端口与协议（接口）

**P1** · 新增（2026-09-28）

对 `wp-sg-renamed` 逐条发请求（`POST /security_groups/<组>/rules`、`PATCH /security_groups/<组>/rules/<规则>`，请求体写文件再 `-d @file`），方向一律 `ingress`，来源一律 `10.9.0.0/16`（避免和默认规则撞上而被「幂等」返回已有记录）：

| 请求 | 预期 |
|---|---|
| POST tcp，不传端口 | 200，存 1 / 65535 |
| POST tcp，只传 `port_min: 8080` | 200，存 8080 / 8080 |
| POST tcp，`port_min: 0` | **400**（`TCP/UDP port must be 1-65535`） |
| POST tcp，`port_max: 70000` | **400**（`Invalid input JSON`） |
| POST tcp，`port_min: 90, port_max: 80` | **400** |
| POST icmp，`port_min: 8, port_max: 0` | 200，存 8 / 0；节点链里是 `--icmp-type 8/0` |
| POST icmp，`port_min: 0, port_max: 0` | 200，存 0 / 0，是一条**新**规则（不是 -1，也不会被当成 8/0 那条） |
| POST icmp，不传端口 | 200，存 -1 / -1 |
| POST icmp，`port_min: 255` | **400**（type 0–254） |
| POST icmp，只传 `port_max: 3` | **400**（`ICMP code requires ICMP type`） |
| POST gre | 200，存 -1 / -1 |
| 把第一条 tcp 规则原样再 POST 一次 | 200，返回的 `id` 与第一次**相同**（幂等） |
| POST 不带 `remote_cidr` / `remote_cidr: "1.2.3.4"` / `direction: "bogus"` | **400** |
| PATCH 8080 那条只改 `remote_cidr: 10.8.0.0/16` | 200，端口仍是 8080 / 8080 |
| PATCH 8080 那条 `protocol: icmp`，不传端口 | 200，存 -1 / -1 |
| 再 PATCH 回 `protocol: tcp`，不传端口 | **400**（`port_min/port_max are required when changing protocol to tcp/udp`） |
| PATCH `protocol: tcp, port_min: 443` | 200，存 443 / 443 |
| 把 443 那条 PATCH 成 `port_min: 1, port_max: 65535, remote_cidr: 10.9.0.0/16`（与第一条 tcp 规则完全相同） | **400**（`An identical security rule already exists in this security group`） |

- [ ] 上表逐条符合
- [ ] `wp-vm` 挂着这个组时，每次成功的增删改都立即反映到节点上的 `secgroup-in-<tap>` / `secgroup-out-<tap>`
  > **回归点**：ICMP type / code 可以是 0。模型字段加了 GORM `default` 时 0 会被换成默认值；按结构体 `Where` 查重会跳过值为 0 的字段、匹配到别的规则。现在建 / 改 / 查重都用 map 条件（CLAUDE.md「零值有业务含义的字段」）

## SG-08 权限

**P1** · 新增（2026-09-28）· 账号用 `TC-03 NET-08` 准备的 R（Admin 组织只读）/ W（Admin 组织读写）/ X（另一组织读写）

| 操作 | R | W | X |
|---|---|---|---|
| `GET /security_groups/<wp-sg-renamed>` | 200 | 200 | 400（按组织过滤查不到） |
| `POST /security_groups/<wp-sg-renamed>/rules` | **403** | 200 | 400 |
| `DELETE` 该组的一条规则 | **403** | 204 | 400 |
| `PATCH /security_groups/<wp-sg-renamed>` `{"description":"r"}` | **403**（100004 `Not authorized to update the security group`） | 200 | 400 |
| `PATCH` 一个**组织级**（不在 VPC 里）的非默认组 `{"is_default":true}` | 403 | **403**（`Not authorized to change the default security group of the organization`，只有组织管理员能换） | 400 |
| `POST /security_groups` 不带 VPC | 403 | **403**（组织级的组要管理员） | 403 |
| `POST /security_groups` 带 `wp-vpc` | 403 | 200（名字用 `wp-sg-w`） | 400（VPC 查不到） |
| `DELETE /security_groups/<wp-sg-w>` | **403** | 204 | 400 |

- [ ] 上表逐条符合
  > X 必须是另一组织的**读写成员**。若用的是组织**管理员**（如 2026-09-28 那轮的共享账号 `wpr_ext_0928b`），「不带 VPC 建组」一行会是 200（组织管理员按设计可以建组织级的组），不算缺陷，记得用 X 自己的 token 把建出的组删掉（管理员的列表只看 Admin 组织，看不到它）。组织级组那一行要先由管理员（系统管理员 / 组织管理员）不带 VPC 建一个 `wp-sg-org`，用完删掉
- [ ] 只读成员改不了安全组：R 的 PATCH 403，名称 / 描述 / 默认标记都不变；R 发 `{"is_default":true}` 同样 403（部署后可以真的发，预期被拒；万一成功说明修复没生效，记 FAIL，用管理员把 `wp-vpc` 的默认组切回 native）
- [ ] VPC 里的组由写成员切成默认组（W 对 `wp-sg-w` 发 `{"is_default":true}`）→ 200，原默认组 `is_default=false`、路由器 `default_sg` 指向新组；**切换失败时整个请求返回错误**，不会出现「名字改了、默认组没切」的半完成状态
- [ ] 系统管理员对**别的组织**的组织级组切默认，改的是**那个组织**的默认组（`organizations.default_sg`），不是系统管理员自己的组织
  > **2026-09-30 已修（`api/src/services/secgroup.go`：`Update` 加写权限检查；组织级组切默认限组织管理员；`Switch` 的错误不再被忽略；`Switch` 按组的所属组织取默认组），2026-10-01 已部署，按本条判定**
  >
  > 原记录（D5，2026-09-28）：`SecgroupAdmin.Update` 没有任何权限检查，只读成员能改名称、描述，甚至 `is_default:true` 切成 VPC 的默认组；`a.Switch(...)` 的返回值被丢掉
- [ ] 响应里只有业务消息（error_code 100004 / 141001），没有数据库原始报错

## 历史缺陷回归点汇总

| # | 现象 | 根因 |
|---|---|---|
| 1 | 节点重启后 br756 上所有虚拟机的安全组被绕过 | FORWARD 链插入位置，见 SG-05 |
| 2 | 列表页 `vpc` 列显示别的安全组的 VPC | GORM Statement 复用，见 SG-01 |
| 3 | 超过 50 个组看不到 | 前端不传 limit，见 SG-01 |
| 4 | 清空描述无效 | Patch payload 用值类型而非指针，见 SG-04 |
| 5 | 删除规则失败无提示 | 用了原生 `confirm()`/`alert()`，见 SG-04 |
| 6 | `query` 参数可注入绕过组织过滤 | 安全组列表曾把 `query` 直接当 WHERE 拼进 SQL。见 `TC-13 SEC-01`、SG-01 的 `query=%` |
| 7 | 上游 PET-1344「安全组规则重叠检查」**有意未合入**（上游自己 revert 了） | 不要把「允许重叠规则」当 bug |
| 8 | 详情页只改描述必定 400；对任何默认组做任何修改都 400（2026-09-20 修，`c0770e1a`） | PATCH 的 `name` 是 required、`is_default` 不传即 false 被当成「取消默认」，见 SG-04 |
| 9 | 规则留空 CIDR 或漏掩码提交后 400，并把 gin 原始报错透给用户（2026-09-20 修，`c0770e1a`） | 后端 `remote_cidr` 是 `binding:"cidrv4"`，前端原先不校验；现在 `isValidCIDRv4` 先挡，见 SG-03 |
| 10 | ICMP type / code 为 0 的规则存成默认值或查重时匹配到别的规则 | 零值字段用了 GORM `default` / 结构体 `Where`，见 SG-07 |
| 11 | 只读成员能改安全组的名称、描述、默认标记；切默认组失败被忽略（D5，2026-09-28；2026-09-30 修，2026-10-01 已部署） | `SecgroupAdmin.Update` 没有权限检查，`Switch` 的错误没接住，见 SG-08 |
| 12 | 系统管理员给别的组织切组织级默认组，改到了自己组织的默认组（2026-09-30 审查时发现并修，2026-10-01 已部署） | `Switch` 用调用方的 `OrgID` 取组织，见 SG-08 |
| 13 | 新建 VPC 时别的某个安全组的 `is_default` 被清掉（2026-09-30 修，2026-10-01 已部署） | `Switch` 在路由器还没有默认组时 `Take(ID=0)`，见 `TC-03` NET-01 |
| 14 | 规则弹窗没用 `BaseModal`（无 ESC、不锁滚动）；改成表单后回车会直接保存默认规则（D16，2026-09-28；2026-09-30 修，2026-10-01 已部署） | 自写遮罩；见 SG-03 最后一项 |
| 15 | 「VPC」筛选下拉超过 50 个 VPC 缺项（FAIL-8 同类；2026-09-30 修，2026-10-01 已部署） | 取列表不带 `limit`，见 SG-01 |
