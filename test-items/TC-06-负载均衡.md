## 设计约定（判定预期的依据）

- 每个 LB 一个 VRRP 实例，主备各在一个节点（zone 内 `select=` 调度，第二个节点排除主节点）。zone 里只有一个可用节点时只在主节点上运行（LB-07b）。
- VPC 路由器 netns 内跑 **keepalived**（浮动 IP 挂在 `te-<router>-<vlan>`）和 **haproxy**（`source` 用本端 VRRP 地址访问后端）。
- 配置目录：`/opt/cloudland/cache/router/router-<N>/{vrrp-<VrrpInstanceID>,lb-<LoadBalancerID>}/`（都是库里的自增 ID，不是 UUID）；pid 文件 `vrrp-<id>/keepalived.pid`（父进程）、`vrrp-<id>/vrrp.pid`（VRRP 子进程）、`lb-<id>/haproxy.pid`。
- keepalived 两端都以 `state BACKUP` + `nopreempt` 启动，按角色给优先级（MASTER 110 / BACKUP 100）。**写 `state MASTER` 时 nopreempt 不生效**，进程重启会抢回主。
- haproxy 的 server 名是 `be-<backend ID>`，listen/frontend 名 `lb-<LB ID>-lsn-<listener ID>`；stats socket `lb-<id>/admin.sock`（`expose-fd listeners`），另有只绑 `127.0.0.1:8080` 的统计页（所以在 netns 里 `ss -ltn | grep 8080` 会多一行 127.0.0.1，不是冲突）。
- **VRRP 子网**：每个 VPC 一个 `192.168.196.0/24`（`services/loadbalancer.go` 写死），第一个 VRRP 实例建它（名字 `<LB 名>-<纳秒时间戳>`），`.1` 是各节点都有的 anycast 网关；**每个实例分一对新地址**（第一个 `.2`/`.3`，第二个 `.4`/`.5`……），但**网卡与 MAC 同一 VPC 同一节点共用一块**；VRID 存在 `vrrp_instances.vrid`，**按 VRRP 子网**取 1–255 的最小空闲值。建 VRRP 子网时 VPC 的 native 安全组自动加上放行 `192.168.196.0/24` 的 tcp/udp 规则（`setRouting`），所以挂 native 组的后端收得到 haproxy 的健康检查与请求。
- 计算节点必须装 haproxy，且**系统自带的 `haproxy.service` 要禁用**（部署脚本曾只装 keepalived，接口全部 `available` 而 LB 实际不监听）。

### ⭐ 最容易误判的一点

**创建 LB 时节点上只建 VRRP 网卡与地址，不起 keepalived / haproxy。**

`create_keepalived_conf.sh` 收到的 `floating_ips` 为空时，会**删掉 `vrrp-<id>` 目录并退出**。所以「LB 状态 `available`，但节点上既没有 `vrrp-<id>` 目录也没有进程」是**正常的**。要**绑定浮动 IP 之后**两个进程才起来。

（`create_haproxy_conf.sh` 也要先有 `vrrp-<id>/keepalived.conf`，否则报 `No such file or directory`。）

排查顺序：`vrrp_instances` 的 `hyper`/`peer` 是否落库 → 节点上有没有 `ns-<vrrp vlan>` 与地址 → 有没有浮动 IP。

### 测试脚本自身的坑

- **`pgrep` / `pkill` 不分网络命名空间**：`ip netns exec router-<N> pkill haproxy` 会杀掉**整台主机**的 haproxy（包括 `rb-lb` 的）。杀进程一律按 pid 文件；数进程按配置路径 `pgrep -fc "[h]aproxy.*lb-<id>/"`（方括号防止匹配到 ssh 命令自身，否则计数多 1）。
- 界面：work-01 的 nginx 停在 09-27（`facff649`），但负载均衡两个页面、`api/networks.ts` 与基础组件自那以后没改（`git diff facff649 HEAD -- web/src/views/dashboard/LoadBalancer*.vue web/src/api/networks.ts web/src/components/base web/src/components/modals` 为空），所以 work-01 上的 `/root/console-test/lb*.js` 仍然有效；按 CLAUDE.md 约定也可以在本机 5173 跑（`BASE` 改成 `http://127.0.0.1:5173`，`/api` 代理到的仍是 work-01 真实环境）。`lb.js`–`lb4.js` 是**写入脚本且没有兜底拦截**：执行前给 context 加上 `00-环境与前置.md` 第 3 节的拦截，只放行 `/api/v1/load_balancers` 开头的写请求；`lb-status.js` 是只读的（已带拦截）。

## LB-06 haproxy 重载不丢请求

**P1** · 在临时 LB 上做，**不要改 `rb-lb` 的配置**（只读打流量测不出重载）

办法：反复增删第二个后端 `wp-be-x`，地址与 `wp-be` 相同（`<web ip>:8080`）。后端唯一索引是「名称 + 监听器 + 地址」，名称不同就能重复；每次增删都会重新下发 haproxy 配置并重载，而新加的 server 本来就是好的，不会因为「重载后先当作 UP」把请求打到坏地址上（那样的失败与 `-x` 无关）。

```bash
# terminal 1: traffic
ssh work-01 'ok=0; fail=0; for i in $(seq 1 600); do
  curl -s -m 3 -o /dev/null -f http://52.117.101.158:8080/ && ok=$((ok+1)) || fail=$((fail+1)); sleep 0.1
done; echo "ok $ok fail $fail"'
# terminal 2: 6 add/delete rounds of wp-be-x (POST, then DELETE the returned id), 5 s apart
```

- [ ] 6 轮增删（12 次重载）期间失败数为 **0**；两个节点的 `lb-<lbid>/haproxy.pid` 每次都换了新进程，旧进程退出

## LB-07 进程守护与并发

**P1** · 在临时 LB 上做。**杀进程一律按 pid 文件**，不要 `pkill`（见「测试脚本自身的坑」）

```bash
# kill the haproxy of this LB on the BACKUP node (no traffic impact), wait for a heartbeat (1-20 s) to bring it back
ssh work-0X 'd=/opt/cloudland/cache/router/router-<N>/lb-<lbid>; kill -9 $(cat $d/haproxy.pid); sleep 25; pgrep -fc "[h]aproxy.*lb-<lbid>/"'
```

- [ ] haproxy 被杀后下次心跳拉起（`check_lb_process.sh`，最坏中断近 20 秒；备节点上被杀不影响流量）
- [ ] 主节点 keepalived **父进程** `kill -9 $(cat vrrp-<vid>/keepalived.pid)` → 子进程随之退出并**自行摘除浮动 IP**，对端接管，打流量时丢约 1 个请求
- [ ] 主节点这个 LB 的**全部进程**同时 `kill -9 $(cat vrrp-<vid>/keepalived.pid) $(cat vrrp-<vid>/vrrp.pid) $(cat lb-<lbid>/haproxy.pid)` → 对端**约 3–4 秒后接管**（VRRP 子进程被 -9 时不发优先级 0 通告，对端要等 master_down_interval），期间请求失败（每 0.1 秒一次的探测约 25 次 `000`），残留浮动 IP 由守护脚本摘除（5–31 秒，取决于心跳），摘地址后再拉起 keepalived
  > 原写「立即接管、0 失败」，2026-09-28 两次实测都中断约 3 秒（+0.4 s 至 +3.4 s），按 VRRP 协议这是预期；0 失败只可能是探测间隔太稀。只杀父进程时子进程会发通告，那一项仍是 0–1 个失败
- [ ] 被拉起的 keepalived **即使优先级更高也不抢主**（`.158` 留在对端）
- [ ] 全程 `rb-lb` 10/10（它的进程不受影响）

### 并发互斥

「判断存活 → 替换配置 → 启动/重载」用 `flock $run_dir/lb_process.lock` 互斥；守护脚本拿不到锁就跳过本轮。要在 haproxy **不在**时并发跑守护脚本才测得出（进程活着时每个脚本都直接跳过）：

```bash
ssh work-0X 'd=/opt/cloudland/cache/router/router-<N>/lb-<lbid>; kill -9 $(cat $d/haproxy.pid)
for i in $(seq 1 15); do /opt/cloudland/scripts/backend/check_lb_process.sh >/dev/null 2>&1 & done; wait
sleep 2; pgrep -fc "[h]aproxy.*lb-<lbid>/"'
```

- [ ] 15 个并发守护脚本之后，这个 LB 的 haproxy 进程数是 **1**（`rb-lb` 等其他 LB 的进程数不变）
  > **回归点**：无锁时实测起出 15 个 haproxy。另外，**持锁时启动的 keepalived / haproxy 必须带 `9>&-`**，否则守护进程继承描述符、锁永远不释放（判定：`ls -l /proc/$(cat $d/haproxy.pid)/fd | grep lb_process.lock` 为空）。

## 手工起 keepalived 的注意事项

`notify_master`（`set_route_table.sh`）依赖环境变量 `ROUTES_FILE` / `KEEPALIVE_CONF` 恢复 fip 路由表的默认路由。浮动 IP 被摘除时该默认路由随之消失，**手工启动 keepalived 必须带上这两个变量**（用 cloudrc 的 `start_keepalived`），否则切换后回包出不去。2026-09-27 起 `set_route_table.sh` 要求 `ROUTES_FILE` 里**每一行**都成功（两个 VLAN 的浮动 IP 有两张 fip 表），失败的行每 2 秒重试、最多 5 分钟。

## 从路由器 netns 验证后端

必须用 `curl --interface <VRRP 地址>`。VPC 网关与 VRRP 子网网关都是 anycast，默认源地址的回包会落到本地路由器。
