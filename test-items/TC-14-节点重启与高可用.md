# TC-14 节点重启与高可用（HA）

优先级 **P2** · ⚠️ **破坏性：会真实重启计算节点** · 约 60 min

> 只在改动涉及**节点恢复流程**（`recover_loadbalancer`、`report_rc.sh`、`add_fwrule.sh`、`create_link.sh`、cloudlet-go、部署脚本、网络配置）时才跑。
> 重启前先确认没有别人在用该环境。

节点重启是本项目**历史上出问题最多**的场景 —— 很多 bug 只有真实重启才暴露，模拟测不出来。

## HA-02 安全组必须重新生效

**P0**（在重启场景下）

这是重启后**最危险**的一条。

```bash
ssh work-0X 'iptables -S FORWARD'
```

- [ ] 安全组跳转（`apply_fw` 插的第 3 条）排在网桥内部放行（`-i brX -o brX -j ACCEPT`）**之前**
- [ ] 兜底 REJECT 在**最后**
- [ ] 从外部访问该节点上虚拟机的**未放行端口** → **超时**（不是 connection refused）

### 缺陷背景

`report_rc.sh` 的 `sync_instance` 曾用 `iptables -I FORWARD 2` 插入，导致**节点重启后，开机时已存在的网桥（如 br756）上所有虚拟机的安全组被完全绕过**。来自上游 `77e1b809` + `d788855e`，分叉时带入。

修法：`sync_instance` 与 `apply_bridge` 都改为**追加到链尾**，再把兜底 REJECT 移到最后。

## HA-03 负载均衡恢复的三个依赖

**P0**（在重启场景下）

节点重启后 LB 能恢复，依赖三件事 —— 这三条都是 2026-09-17 真实重启 work-02 才发现的。

### 3.1 VXLAN 转发条目与邻居表项

`bridge fdb` / `ip neigh` 重启后**全部丢失**。

```bash
ssh work-0X 'bridge fdb show | grep -c "dst "; ip neigh show | grep -c PERM'
```

- [ ] 重启后条目被重新下发（`recover_loadbalancer` 在 `set_vrrp_ip.sh` **之后**调用 `sendFdbRules`）
- [ ] **顺序不能反** —— 反了的话 VRRP 网卡会被按网关规则的 MAC 先建出来

**不下发的后果**：

- 重启过的节点**访问不到其他节点上的后端**（haproxy 全部 DOWN，接管后返回 503）
- VRRP 单播心跳也发不出去（VXLAN 不泛洪，ARP 只能靠静态邻居表项），对端被拉起的 keepalived 收不到心跳，会以更高优先级**抢主**

- [ ] 重启后**没有出现双主**
  ```bash
  ssh work-01 'for h in local work-02 work-03; do echo -n "$h 持有 rb-lb 浮动IP: "
    c="ip netns exec router-8 ip -4 -br addr 2>/dev/null | grep -c 52.117.101.151"
    if [ "$h" = local ]; then sh -c "$c"; else ssh -n root@$h "$c"; fi
  done'
  ```
  期望：**只有一个节点是 1**

### 3.2 子网网关口

`add_fwrule.sh` 原先按**网桥**是否存在决定是否建子网网关口。网桥由 NetworkManager 持久化、开机自动重建，但**路由器 netns 内的网关口不会** —— 所以重启后永远补不上。

- [ ] 现在按 `ns-<vni>` 是否存在判断
- [ ] 重启后 netns 里的网关口都在
  ```bash
  ssh work-0X 'for n in $(ip netns list | awk "{print \$1}"); do echo -n "$n: "; ip netns exec $n ip -br link show | grep -c "^ns-"; done'
  ```

### 3.3 首次心跳不被阻塞

`report_rc.sh` 的 `sync_instance` 原先**每台虚拟机都等 WDS 设备文件最多 200 秒**。本地存储环境永远等不到 → 首次心跳被阻塞 → **节点离线约 7 分钟**、虚拟机和 LB 恢复全部推迟。那段等待已随 WDS 一并删除（2026-09-22）。

- [ ] 重启后首次心跳在 ~42 秒内到达（不是 7 分钟）
- [ ] **心跳里不做无上限的等待**：池的探测在每池一个的后台进程里，心跳只读状态文件
  > 同类风险：`paused_nospace` 会对暂停的域调 `virsh`，池写满时 libvirtd 本身可能卡住。判定方法：池写满 + 多台虚拟机暂停时，心跳间隔仍是 1–20 秒，节点不被判离线
- [ ] 池没挂上时虚拟机进**待启动列表**（上报 `pending_storage`），池就绪后下一次心跳自动启动并补发 sync（详见 `TC-16` STO-07）
- [ ] 重启后 `local-hdd` **自动挂载**（fstab 带 `nofail`），池里有盘的虚拟机正常启动
  ```bash
  ssh work-0X 'mountpoint /opt/cloudland/pools/*; grep cloudland/pools /etc/fstab'
  ```
  > **2026-09-23 已在 work-03 实测**（脚本 work-01 `/root/st-reboot-prep.sh` 布置测试机、`/root/st-reboot.sh` 重启并记时间线）：一台系统盘与数据盘都在 `local-hdd` 的虚拟机，重启后开机 +12 秒池挂载（早于 cloudlet 启动，所以走正常启动、待启动列表为空）、+26 秒 cloudlet 启动、约 +43 秒注册、+43～47 秒 4 台虚拟机全部起来、约 +55 秒首次心跳与池上报，两块盘上的标记完好。**未覆盖**：「池晚到」触发待启动列表的真实开机路径（这次池挂得比 cloudlet 早）、带 RAID1 的池（降级阵列的开机装配与 `x-systemd.device-timeout`）
  >
  > ⚠️ 重启会让该节点上的 LB 后端下线：`rb-lb` 目前**只靠 work-03 上的 rb-be1**，重启 work-03 期间 LB 全部 503（见 `00-环境与前置.md` 第 4 节）

## HA-04 VRRP 网卡 MAC 纠正

**P0**（在重启场景下）

VRRP 子网网卡与普通子网网关口**同名**（都是 `ns-<vni>`）。

`set_vrrp_ip.sh` 的逻辑：设备已存在且 MAC **等于网关规则生成值**（cloudrc `subnet_gw_mac`：`52:<vni>:<hostid>`）时，改为数据库记录的 VRRP MAC；否则沿用（同一 VPC 多个 LB 共用该网卡）。

**不纠正的后果**：节点重启后 `launch_vm sync` 下发的转发条目可能**先于** LB 恢复把它按网关口建出来 → 对端心跳收不到 → 双主。

```bash
ssh work-0X 'ip netns exec router-8 cat /sys/class/net/ns-<vrrp vni>/address'
ssh work-01 'docker exec cloudland-postgres psql -U postgres -d cloudland -t -c "select name,mac_addr,hyper from interfaces where type='"'"'vrrp'"'"';"'
```

- [ ] 节点上的 MAC 与数据库记录的 VRRP MAC **一致**

> 说明：第三次真实重启（2026-09-17）时，恢复流程的 `set_vrrp_ip.sh` **恰好先于** `launch_vm sync` 的 `add_fwrule.sh` 执行，「网卡被按网关口抢先建出」的竞态**没有自然触发**。该路径目前只由手工模拟验证过 —— 每次重启测试都值得重点看这一条。

## HA-07 控制节点重启

**P2** — 风险更高，谨慎

- [ ] 所有 `unless-stopped` 容器被拉起
- [ ] **dnsmasq 容器在**
  > **回归点**：用 `docker kill -s <信号>`（含 Docker API `/containers/<id>/kill`）给容器发重载信号，即使只是 SIGHUP，Docker 也会把容器标记为**手动停止**（`HasBeenManuallyStopped=true`），`unless-stopped` 的容器在 Docker/宿主机重启后**不会被拉起**。dnsmasq 曾因此重启后不在。
  > **改用 `docker exec <容器> kill -HUP 1`。**
- [ ] 控制面 DNS 可用（`dig @<INTERNAL_IP>`；dnsmasq 日志**不进** `docker logs`）
