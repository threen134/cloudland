- 事后是否把 VPN 网关的主节点切回原节点**由用户决定**；切回办法同 `TC-17` VPN-04（在当前主节点上按 pid 文件 `kill -9` 该网关的 keepalived，`vrrp-<VrrpInstanceID>/keepalived.pid`），每切一次都会再中断一次到 IBM 的隧道。

## HA-02 安全组必须重新生效

**P0**（在重启场景下）

这是重启后**最危险**的一条。目标虚拟机：重启 work-03 用 **net-c**（直接在公网子网 `public-756` 上，`.149`，正是当年出事的 br756）；重启 work-02 用 **net-a**（浮动 IP `.150`）。先只读看它的安全组，挑一个没放行的 TCP 端口。

```bash
ssh work-0X 'iptables -S FORWARD'
# from outside the cluster (the local machine), not from work-x
curl -s -m 5 -o /dev/null -w "%{http_code} %{time_total}\n" http://52.117.101.149:<unopened port>/
```

- [ ] 安全组跳转（`apply_fw` 插的第 3 条）排在网桥内部放行（`-i brX -o brX -j ACCEPT`）**之前**
- [ ] 兜底 REJECT 在**最后**
- [ ] 从外部访问该虚拟机的**未放行端口** → **超时**（不是 connection refused）；已放行的 22 端口能连

### 缺陷背景

`report_rc.sh` 的 `sync_instance` 曾用 `iptables -I FORWARD 2` 插入，导致**节点重启后，开机时已存在的网桥（如 br756）上所有虚拟机的安全组被完全绕过**。来自上游 `77e1b809` + `d788855e`，分叉时带入。

修法：`sync_instance` 与 `apply_bridge` 都改为**追加到链尾**，再把兜底 REJECT 移到最后。

## HA-03 负载均衡恢复的三个依赖

**P0**（在重启场景下）

节点重启后 LB 能恢复，依赖三件事 —— 这三条都是 2026-09-17 真实重启 work-02 才发现的。恢复由心跳按 `boot_id` 触发：`report_rc.sh` 的 `recover_loadbalancer` 回调 → clapi 对这个节点上每个 LB 依次 `set_vrrp_ip.sh` → 重发 fdb → `create_keepalived_conf.sh` → `create_haproxy_conf.sh` → `create_lb_floating.sh`。

### 3.1 VXLAN 转发条目与邻居表项

`bridge fdb` / `ip neigh` 重启后**全部丢失**。

```bash
ssh work-0X 'bridge fdb show | grep -c "dst "; ip neigh show | grep -c PERM'
```

- [ ] 重启后条目被重新下发（`recover_loadbalancer` 在 `set_vrrp_ip.sh` **之后**调用 `sendFdbRules`；VPN 网关的 `VpnRecoverNode` 同样的顺序）
- [ ] **顺序不能反** —— 反了的话 VRRP 网卡会被按网关规则的 MAC 先建出来

**不下发的后果**：

- 重启过的节点**访问不到其他节点上的后端**（haproxy 全部 DOWN，接管后返回 503）
- VRRP 单播心跳也发不出去（VXLAN 不泛洪，ARP 只能靠静态邻居表项），对端被拉起的 keepalived 收不到心跳，会以更高优先级**抢主**

- [ ] 重启后**没有出现双主**（`rb-lb` 与每个主备 VPN 网关都查）
  ```bash
  ssh work-01 'for h in local 10.191.202.29 10.191.202.13; do echo -n "$h: "
    c="for r in 8 50 51; do echo -n \"router-\$r=\"; ip netns exec router-\$r ip -4 -br addr 2>/dev/null | grep \"^te-\" | grep -oE \"52\.117\.101\.1[0-9]{2}\" | xargs | tr \" \" \",\"; echo -n \" \"; done"
    if [ "$h" = local ]; then sh -c "$c"; else ssh -n root@$h "$c"; fi; echo
  done'
  ```
  期望：`.151`、`.152`、`.153`、`.154`/`.155` 每个地址**只出现在一个节点上**（`.156`、`.157` 是 `aax-gw` 各节点的固定地址，本来就一边一个）

### 3.2 子网网关口

`add_fwrule.sh` 原先按**网桥**是否存在决定是否建子网网关口。网桥由 NetworkManager 持久化、开机自动重建，但**路由器 netns 内的网关口不会** —— 所以重启后永远补不上。

- [ ] 现在按 `ns-<vni>` 是否存在判断
- [ ] 重启后 netns 里的网关口都在
  ```bash
  ssh work-0X 'for n in $(ip netns list | awk "{print \$1}"); do echo -n "$n: "; ip netns exec $n ip -br link show | grep -c "^ns-"; done'
  ```

### 3.3 首次心跳不被阻塞

`report_rc.sh` 的 `sync_instance` 原先**每台虚拟机都等 WDS 设备文件最多 200 秒**。本地存储环境永远等不到 → 首次心跳被阻塞 → **节点离线约 7 分钟**、虚拟机和 LB 恢复全部推迟。那段等待已随 WDS 一并删除（2026-09-22）。

- [ ] 重启后首次心跳在约 1 分钟内到达（不是 7 分钟）
- [ ] **心跳里不做无上限的等待**：池的探测在每池一个的后台进程里，心跳只读状态文件；池没就绪的虚拟机进待启动列表，不在心跳里等（详见 HA-09）
  > 同类风险：`paused_nospace` 会对暂停的域调 `virsh`，池写满时 libvirtd 本身可能卡住（心跳里的 `virsh` 一律加 `timeout`）。判定方法：池写满 + 多台虚拟机暂停时，心跳间隔仍是 1–20 秒，节点不被判离线

## HA-04 VRRP 网卡 MAC 纠正

**P0**（在重启场景下）

VRRP 子网网卡与普通子网网关口**同名**（都是 `ns-<vni>`）。同一 VPC 在同一节点上的所有 VRRP 实例（LB 与 VPN 网关）**共用这一块网卡与 MAC**（rb-vpc 里 `rb-lb` 与 `a1` 就是）。

`set_vrrp_ip.sh` 的逻辑：设备已存在且 MAC **等于网关规则生成值**（cloudrc `subnet_gw_mac`：`52:<vni>:<hostid>`）时，改为数据库记录的 VRRP MAC；否则沿用（同一 VPC 多个实例共用该网卡）。

**不纠正的后果**：节点重启后 `launch_vm sync` 下发的转发条目可能**先于** LB 恢复把它按网关口建出来 → 对端心跳收不到 → 双主。

按 HA-00 查出来的每一行（`router_id`、`vlan`、`mac_addr`）核对：

```bash
ssh work-0X 'ip netns exec router-<router_id> cat /sys/class/net/ns-<vlan>/address'
```

- [ ] 节点上的 MAC 与数据库记录的 VRRP MAC **一致**（rb-vpc 的 VNI 是 `5670329`，`ibmx` / `ibmr` / `aax` 分别是 `5708994` / `9867179` / `10210351`，以 HA-00 的查询为准）

> 说明：第三次真实重启（2026-09-17）时，恢复流程的 `set_vrrp_ip.sh` **恰好先于** `launch_vm sync` 的 `add_fwrule.sh` 执行，「网卡被按网关口抢先建出」的竞态**没有自然触发**。该路径目前只由手工模拟验证过 —— 每次重启测试都值得重点看这一条。
