## 设计约定（判定预期的依据）

- **组成员由 clapi 选节点**，下发单节点 `select=group-zone-<z>:<节点>`，cland 只复核资源；不选放置组的创建和迁移代码路径不变（控制串仍是多节点 `select=` 或管理员的 `inter=`）。
- **占用**（方案 §2.2）：`instances.hyper`（已落地）、`hyper = -1` 且 provisioning / deleting 时的 `placement_hyper`（创建中）、进行中迁移的 `target_hyper`（迁移期间源和目标都占）。**卡住的记录继续占**，组详情标 `stale_provisioning` / `stale_migration`。
- **并发**：创建、迁移、删除组都先 `SELECT ... FOR UPDATE` 锁放置组那一行。
- **严格**约束平台自己不破坏：放不下就 409，创建整批回滚、维护腾空记 `not_doing`；只有系统管理员迁移时带 `ignore_placement` 能破坏。**尽量**约束放不下时放宽。
- **严格集中整组迁移**：源节点上的本组成员必须都在同一次请求里、都能迁，且锚点要接得住全部（CPU / 内存按各台规格求和，其他池的盘按池求和），否则一台都不迁。界面的迁移弹窗一次只迁一台，**整组迁移只能经维护腾空或接口一次传多台**。
- **错误码**：111701 不存在 404、111702 重名 409、111703 有成员 409、111704 严格分散无空节点 409、111705 严格集中锚点放不下 / 不可用 409、111706 冲突 400、111707 超过 50 个 409、111708 严格集中组迁移中 409。

### ⭐ 最容易误判的几点

- **409 说「没有空节点」，可数一数成员对不上**：多半有创建中或卡住的成员占着节点，消息末尾会点名（`members being created` / `stuck members`）。
- **严格集中组的成员单独迁移被拒是预期行为**（400，消息写明同节点上哪台没一起请求）。
- **普通用户看不到节点名**，只有 `host_slot`（组内节点编号）；系统管理员多一列节点名。

- 三节点都在 `zone0`：work-01 hostid 1、work-02 hostid 4、work-03 hostid 3。

```bash
# 建组（策略、严格、可用区建好后不能改）
api POST /placement_groups '{"name":"pg-spread","policy":"spread","strict":true,"zone":"zone0"}'
# 在组里建云服务器：只多一个 placement_group
api POST /instances '{"hostname":"pg-s","count":3,"placement_group":{"id":"<组 uuid>"}, ...}'
# 分布：host_slot 一样的就在同一台
api GET /placement_groups/<组 uuid> | jq '{compliant, host_count, members: [.members[] | {hostname, status, host_slot, target_slot, hypervisor, stale_provisioning, stale_migration}]}'
```

### 数据库核对（通用）

```bash

```
