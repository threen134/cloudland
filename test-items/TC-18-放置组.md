## 设计约定（判定预期的依据）

- **组成员由 clapi 选节点**，下发单节点 `select=group-zone-<可用区 ID>:<节点>`（zone0 的 ID 是 1），cland 只复核资源；不选放置组的创建和迁移代码路径不变（控制串仍是多节点 `select=` 或管理员的 `inter=`；系统盘在其他本地池时是 `bootHost` 选出的单节点 `select=`）。
- **占用**（方案 §2.2）：`instances.hyper`（已落地）、`hyper = -1` 且 provisioning / deleting 时的 `placement_hyper`（创建中）、进行中迁移的 `target_hyper`（迁移期间源和目标都占）。**卡住的记录继续占**，组详情标 `stale_provisioning`（创建超过 1 小时）/ `stale_migration`（迁移 1 小时没更新）。
- **并发**：创建、迁移、删除组都先 `SELECT ... FOR UPDATE` 锁放置组那一行，再做存储池准入。
- **严格**约束平台自己不破坏：放不下就 409，创建整批回滚、维护腾空记 `not_doing`；只有系统管理员迁移时带 `ignore_placement` 能破坏。**尽量**约束放不下时放宽；连放宽都放不下时 400（171001 `NoQualifiedHypervisor`）。
- **严格集中整组迁移**：源节点上的本组成员必须都在同一次请求里、都能迁（running / shut_off / 非存储写满的 paused），且锚点要接得住全部（CPU / 内存按各台规格求和，其他池的盘按池求和），否则一台都不迁。本次调用里失败过的成员、更早请求发起还在进行的迁移都会拦住整组。**界面的迁移弹窗选中严格集中组的成员时，自动带上同一节点上的其他成员一起提交**（2026-09-28 代码审查后改的，方案附录 E.6）；维护腾空和接口一次传多台同样走整组规则。
- **`ignore_capacity`** 只跳过存储池容量，放置器照样按真实 CPU / 内存选节点（cland 在选中的单节点上照样复核）。
- **错误码**：111701 不存在 404、111702 重名 409、111703 有成员（含删可用区时组还在）409、111704 严格分散无空节点 409、111705 严格集中锚点放不下 / 不可用 / 整组没有节点接得住 409、111706 冲突 400（可用区不一致、指定的宿主机或迁移目标违反严格约束、严格集中组有成员不能一起迁）、111707 超过 50 个 409、111708 严格集中组迁移中 409。

### ⭐ 最容易误判的几点

- **409 说「没有空节点」，可数一数成员对不上**：多半有创建中或卡住的成员占着节点，消息末尾会点名（`members being created: …` / `members migrating (they hold both hosts): …` / `stuck members: …`）。
- **严格集中组的成员单独迁移被拒是预期行为**（400，111706，消息写明同节点上哪台没一起请求）。
- **严格集中组整组放不下是 409（111705），不是 400**：方案 §10.2 的 PG-21 写的 400 是按初稿写的（2026-09-28 核对代码 `placement_migration.go` 的 `placeStrictPack`）。
- **普通用户看不到节点名**，只有 `host_slot`（组内节点编号，同一台同一个数，从 1 起）；系统管理员多一列节点名（`hypervisor`）和 `migration_id`。
