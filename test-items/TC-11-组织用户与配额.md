## ⭐ 跨服务身份传递（判定预期的依据）

clapi **不掌握用户身份**。`authorize.go` 只从 cpgateway 传来的请求头构造 `MemberShip`，**不查库**（组织 UUID → 本地 ID 的解析有内存缓存）。

cpgateway 转发的头（`cpgateway/src/apis/proxy.go`）：`X-User-ID`、`X-User-Name`、**`X-User-UUID`**、**`X-Org-UUID`**、`X-Org-Name`、`X-Org-Role`、`X-System-Role`、`X-Is-Owner`、`X-Forwarded-Secret`。**`X-Org-ID` 已不再发送**（两边自增主键各自独立，传它没有意义）。

**跨服务只用 UUID 对应，两侧的自增主键各自独立**：

- 组织：`POST /internal/orgs/sync` 传 `{uuid, name, slug, org_type}`，clapi 按 UUID upsert、**本地 ID 由自己分配**，**只按 UUID 匹配、从不按 slug 认领**（唯一的例外是系统组织：控制面的系统组织 `org_type=2` 绑定到区域里唯一的系统组织）；已删的 UUID 再推回 `{"status":"deleted"}`、不会复活。删除走 `POST /internal/orgs/delete {uuid, name}`：区域里这个组织还有资源时 **409**（100218，组织保留、仍可解析；安全组、密钥不计），从没见过的 UUID 留一行软删的「墓碑」。UUID ↔ 本地 ID 的内存缓存只收真实 ID（> 0）、**1 分钟过期**（2026-09-30 改，2026-10-01 已部署；之前「映射建立后不再变化」，见 ORG-10）
- 用户：**完全不同步**，两边 `users` 表各自自增
- clapi 解析不到 `X-Org-UUID`（该组织没同步到这个区域）→ **404**，`error_code` 100204（`OrgNotFound`）；不带这个头 → 当作不属于任何组织，列表全空

### ⚠️ 最容易踩的坑

**cpgateway 所有直接调用 clapi 业务接口的地方都必须带 `X-Org-UUID`。** 不带时 clapi 当作不属于任何组织、**列表全空**。

改造时曾漏了用量对账（`consumption_sync.go`），后果是：每次登录把组织用量**覆盖成 0** → 概览页资源使用率为 0 → **配额限制失效**。

```bash
grep -rn "\"X-Org-UUID\"" cpgateway/src --include=*.go | grep -v _test.go
```

- [ ] 第二条覆盖 `apis/proxy.go`（转发，删除 / 调规格前查资源也用这组头）和 `services/consumption_sync.go`（对账）

### ORG-10b 删除组织后同 slug 新组织不能接管旧资源（2026-09-28 晚新增）

先 resync 组织 C（使它在 clapi 里是真实 ID），在 C 里建放置组 `wp-pg-orgc` → 删除组织 C → 用 C 原来的 slug 新建组织 C2 → 以 C2 登录列放置组、看组织动态。

- [ ] C2 在 clapi 里是**新的一行**（新 `id`），看不到 C 的放置组和动态；clapi 日志**没有** `Adopted existing org`
- [ ] 因为 C 删除时区域里还有 `wp-pg-orgc`，区域拒绝删除（409），C 的旧行保留；C2 同步过来时这行的 `slug` 被清空（日志 `Released slug <slug> held by 1 stale org row(s)`），`uuid`、`id` 和资源都不变、不会交给 C2
  ```bash
  docker exec cloudland-postgres psql -U postgres -d cloudland -Atc "select id, uuid, slug, deleted_at is not null from organizations where uuid in ('<C>','<C2>')"
  docker logs cloudland-clapi --since 10m 2>&1 | grep -E "Adopted existing org|Released slug"
  ```
- [ ] 清理：系统管理员 `DELETE /placement_groups/<wp-pg-orgc>?all_orgs=true`，删组织 C2，再对区域 `PATCH /regions/<uuid> {"is_available":true}`，C 的旧行随全量同步被软删
  > **2026-09-30 已修（`api/src/services/org.go` 删掉按 slug 认领、`releaseOrgSlug` 只清旧行的 slug；cpgateway 删组织推区域），2026-10-01 已部署，部署后按上面三项判定**。
  >
  > 原记录（D1 / FAIL-P3，2026-09-28 晚实测，严重）：`UpsertOrgByUUID` 找不到 UUID 时按 slug「认领」已有行并改写其 uuid，而删除组织不通知区域，于是 C2 接管 C 的全部资源：日志 `Adopted existing org id=37 (slug=...)`，C2 能列出、删除 C 的放置组。部署前的清理：用 C2 的 token 删放置组（此时能删），再删 C2
