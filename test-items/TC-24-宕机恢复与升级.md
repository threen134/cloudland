## 设计约定（判定预期的依据）

- **对账**（§11.4）：节点开机后、或心跳断档超过 60 秒（cloudlet 重连、节点被判离线又回来）后，心跳上报本机定义的所有域（`node_recovered`），clapi 逐台回答：仍归本节点的可以启动、已不归它（被疏散走、已删除）的清掉定义（不碰任何磁盘）、正在迁移的不动；没收到回答前每分钟再问一次。**开机时磁盘在共享池里的云服务器先不启动**（原因「等待对账」），回答说仍归本节点才进待启动列表；只有本地盘的照常启动
- **隔离**（§11.2）：GPFS 在另一台在线的管理节点上 `mmexpelnode -N <节点>`（持久，要 `-r` 才解除）；Ceph 在另一台管理节点上 `ceph osd blocklist range add <地址>/32 <10 年>`，导入的 Ceph 集群用 CloudLand 的客户端身份执行（只能加、不能删）。导入的 GPFS 集群、或唯一的管理节点就是宕机的那台：不能隔离，要管理员确认已断电（`confirm_fenced`）
- **疏散**（§11.3）：`POST /hypers/:uuid/evacuate`，节点必须离线（status 10）满 5 分钟，除非 `confirm_fenced`。全部磁盘都在共享池里的云服务器才能疏散，其他的列为 `not_doing`。每台一条 `type=evacuate` 的迁移记录（`fencing` → `in_progress` → `completed` / `failed`），隔离成功后由 cland 在同可用区、能访问其全部池的节点里选一台执行 `launch_vm.sh`（撤离模式：用已有的系统盘和数据盘重新定义，原来运行的启动、关机的保持关机）。疏散失败时云服务器留在原节点，原因「疏散失败」
- **解除隔离**：节点在线、隔离之后对账过、疏散走的云服务器都已从它上面清掉，clapi 自动解除；也可以在节点详情「解除隔离」立即解除，或「已手工解除」只删记录（导入的 Ceph 集群只能由它的管理员删黑名单）
- **轮换**（§6.6、§8.4）：`POST /storage_clusters/:id/rotate_keys {ssh, client}`，每台成员都要在线。SSH 密钥分三轮：所有节点先同时接受新旧两把（第二行 `…-rotate`）→ 管理节点换用新私钥（Ceph 还要让编排器换钥匙：`config-key` 两项一起写再 `mgr fail`）→ 去掉旧的；集群记录在工具切换时跟着换。Ceph 客户端密钥：`auth get-or-create-pending` → 发到所有节点（keyring 与 libvirt secret）→ **第一次被使用就自动转正**，旧密钥此后不能建立新会话；**已经在跑的 QEMU 不受影响**（Ceph 续期票据不用密钥，mon 重启后也一样），下次启动或迁移时用新密钥
- **升级**（§7.7、§8.7）：`POST /storage_clusters/:id/upgrade`。GPFS：给新版本的安装包（已接受许可、比当前版本新、同一版本类型），先下发到所有节点，再逐台（不在仲裁里的先）：迁走用这个集群存储、正在运行的云服务器（与维护模式相同的迁移）→ 节点上再查一次没有这样的云服务器、所有盘都 up → `mmshutdown` → 装新包 → `mmbuildgpl` → `mmstartup` → 挂载 → `mmchdisk start` 把这台的盘拉回来；全部完成后集群记录换成新包与新版本。之后另起一次 `{finalize: true}`：`mmchconfig release=LATEST`、`mmchfs -V full`（不可逆）。Ceph：各节点装发行版现有的版本（不能比集群旧），再 `ceph orch upgrade start --image <对应镜像>` 并跟到所有守护进程都是新版本；不迁云服务器

### ⭐ 最容易误判的几点

- **节点离线不到 5 分钟时疏散被拒绝是对的**（409，「offline for」）：cland 判离线有 90 秒宽限，再加 5 分钟才确定不是网络抖动；确认断电了可以勾选「已确认断电」跳过
- **疏散后的云服务器要等隔离完成才启动**：迁移记录先停在「隔离中」，GPFS 驱逐一般十几秒、Ceph 加黑名单几秒，然后才下发启动
- **原节点回来后它的云服务器还在原来的列表里一会儿**：被疏散走的那些，原节点开机时域定义还在，对账回答后才清掉；在那之前原节点的上报一律不采信（不会把归属改回去）
- **Ceph 客户端密钥轮换后正在运行的云服务器照常工作**：这不是轮换没生效，是 Ceph 的设计（旧会话不需要密钥续期）；新建会话（`rbd` 命令、新启动的云服务器、热插盘）都用新密钥
- **轮换 Ceph 的 SSH 密钥会让 mgr 切换一次**（几秒）：编排器只有在 mgr 重启时才重新加载钥匙
- **`cephadm set-priv-key` / `set-pub-key` 不能用**：它们各自拿新的一半去配旧的另一半，校验失败就静默保留旧钥匙且返回 0（mgr 日志里 `Public key mismatch`）
- **GPFS 升级中途中止后集群记录还是旧版本**：已升级的节点跑新版本（GPFS 允许混跑），再发起一次升级就能接着做完（已是新版本的节点很快跳过）

## 回归点（实施中发现并修掉的问题）

1. **Ceph 的待定密钥第一次被使用就自动转正**（帮助文本：rotated into place on first use，几秒内生效），不存在「新旧两把都有效、等提交」的窗口；原设计「旧 QEMU 都重启后才提交」的检查步骤已删除（实测旧会话在转正、票据续期、mon 重启后都照常）
2. **`cephadm set-priv-key` / `set-pub-key` 静默回退**：各自校验新的一半与旧的另一半，`Public key mismatch` 后保留旧钥匙且退出码 0；改为 `config-key set mgr/cephadm/ssh_identity_key|pub` 两项一起写再 `mgr fail`，并逐字核对编排器存的钥匙
3. **`cephadm check-host` 走缓存的连接**：钥匙换没换成都会说 OK；核对放在 `mgr fail` 之后（连接都重建了）
4. **节点上留着旧的 `id_ed25519.pub`**（Ceph 部署时为 cephadm 写的）：ssh 先拿它协商、再用新私钥签名，`private key contents do not match public`，新钥匙登录被拒；写私钥时按私钥重写 `.pub`
5. **对账询问的节奏**：等待中的 reconnect 原先每次心跳都问一次（1–20 秒），改为断档 / 开机后立即问、之后每分钟一次；记录里带上开机 ID（运行目录在磁盘上，跨重启保留）
6. **`node_reconcile.sh` 用 `for row in $(jq -c …)`**：值里有空格就被拆开；改为逐行读取并校验每个字段
7. **drain 遇到迁移在建记录前就被拒绝**（没有目标、状态不能迁）时每轮都重试、永远不失败；改为当场按逐台结果失败并写出原因
8. **撤离用的内部元数据（`evacuate`、`data_disks`）会进配置盘**：`build_meta.sh` 的 `network_data.json` 删掉它们（同 S4 的 `boot_disk`）
