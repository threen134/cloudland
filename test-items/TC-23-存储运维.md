## 设计约定（判定预期的依据）

- **健康检查**：选主的 clapi 每分钟给每个 `ready` / `degraded` 集群下发一次 `storage/stc_health.sh`（托管集群发给在线的管理节点，外部集群发给任一在线成员），节点后台检查后回调 `storage_health`。报告写集群的健康与 `health_info`、节点的 `state`、磁盘的 `state`、文件系统容量。超过 5 分钟没有新报告，健康显示「未知」
- **六种告警**（属于系统组织，走系统组织的通知渠道）：

| 告警 | 条件 | 级别 | 什么时候触发 |
|---|---|---|---|
| `StorageClusterUnhealthy` | 健康 warning / error | 按健康 | 持续「告警延迟」（默认 2 分钟） |
| `StorageNodeDown` | 成员在存储软件里不是 active | warning | 持续告警延迟 |
| `StorageDiskDown` | NSD / OSD 不是 up | warning | 持续告警延迟 |
| `CephNearFull` | Ceph 报 nearfull / full / backfillfull | critical | 立即 |
| `StoragePoolUsageHigh` | 共享池用量 ≥ 警告线 / 严重线（默认 80% / 90%） | warning / critical | 立即（clapi 每分钟按池探测算） |
| `StorageFsUnmounted` | 文件型池在某个在线成员上不可用 | critical | 持续告警延迟 |

- 级别变化（例如集群从 warning 到 error、池从 85% 到 95%）先解除旧的、再触发新的；条件消失即解除；删除集群时解除还在触发的
- **曲线**：GPFS 成员由心跳每分钟后台写 `/var/lib/node_exporter/cloudland_storage_<集群UUID>.prom`；共享池用量由池探测写 `cloudland_shared_pool_<池UUID>.prom`；Ceph 由活动 mgr 的 prometheus 模块（9283）导出，Prometheus 任务 `storage_clusters` 经 clapi 的 http_sd 找到 mgr 主机。界面「监控」标签
- **完整日志**：任务详情展开运行，「下载完整日志」→ 节点上传到 clapi（最后 16 MiB）→ 下载 `storage-run-<ID>.log`。节点离线时：已经取回过、而且运行已结束的副本照常给；需要重新取的（运行中、副本比运行旧）给旧副本并提示「宿主机离线，下载的是 … 取回的副本」；从没取回过的 409
- **换盘**：只给健康检查报告不是 up 的盘（状态超过 10 分钟没更新也不给）；新盘要在同一台节点；坏盘不擦除。GPFS 在移除前再查一次：此刻必须是 `down` / `unrecovered`。Ceph 直接 `osd out` → `orch daemon rm` → `osd destroy --force`，不走 `orch osd rm --replace`
- **改角色**：盘角色跟着磁盘走，不在这里改；按建集群的规则检查（仲裁节点 / mon 奇数、管理节点 1–2 台、mgr 1–2 台、管理节点必须是仲裁节点 / mon）；集群命令在**原来的**管理节点上执行（刚加为管理节点的那台还没有 admin keyring）
- **自动加为客户端**：所选可用区里不在集群中的在线节点（开启时已有的也算）逐台加入；失败的那台不再重试
- **孤儿对账**：只报告、不删除

### ⭐ 最容易误判的几点

- **告警晚 2–3 分钟才出来是对的**：健康检查每分钟一轮（报告还要等下一次心跳带回），再加 2 分钟延迟；池用量和 nearfull 是立即的，但池用量要等池探测（30 秒一次）与 clapi 下一轮
- **停掉一个 OSD 后会同时有三条告警**：集群不健康（warning）、磁盘离线；Ceph 还可能因为数据重新分布报别的检查项。都是对的
- **健康「未知」不等于坏了**：检查节点自己没给出报告（命令超时、节点离线）时是未知，告警保持原样
- **Ceph 曲线一开始是空的**：mgr 的 prometheus 模块由健康检查第一次打开，Prometheus 30 秒采一次、速率要 3 分钟窗口，过 4–5 分钟才有曲线
- **Ceph 回环测试盘换掉后，外面那层 `clceph-*` 卷组没了**：是 `backend_disks_resolved` 去掉离开集群的回环盘的卷组（只有回环测试盘有这一层），盘里的数据没擦；真实磁盘上 OSD 直接建在设备上，什么都不动
- **GPFS 的池用量按两份副本算**：写 1 GiB 用量涨约 2 GiB，而且 `df` 在写完后的头几秒还没算全，往里灌数据时要分几步，一次写猛了会顶到配额（100%），池上的云服务器写不进去
- **Ceph 池写到配额就卡住**：池探测判池不可用、不再报用量，严重线告警出不来，测到 94–95% 即可（超出配额约 8% 才拦写，所以 99% 时已经卡住）
- **GPFS 停盘后看护会把它拉起来**：集群没有任务时，看护每分钟 `mmchdisk start` 处于 down 的 NSD，造坏盘时要在下一轮之前提交换盘（换盘任务占着集群时看护不跑）

## OPS-01 健康检查与界面

1. 打开 `gpfs1`、`ceph1` 的详情概览，等 1–2 分钟

**预期**：「健康检查」卡片有最近检查时间与检查节点（管理节点）；GPFS 概况形如 `3/3 nodes active, 3/3 disks up`，Ceph 是 `HEALTH_OK`（或 `HEALTH_WARN` 带消息）；Ceph 有裸容量；节点表「存储软件报告的状态」是 `active`、悬停显示检查时间；磁盘表「报告的状态」全是 `up`；`ceph mgr module ls` 里 prometheus 已打开

## OPS-02 集群不健康 / 节点离线 / 磁盘离线（GPFS）

1. 在 work-03 上 `mmshutdown`（只停 work-03 的 GPFS；work-03 上用 GPFS 盘的云服务器先迁走：`mmshutdown` 会强制卸载）
2. 等 4 分钟，看告警事件；然后 `mmstartup`，等 NSD 被自动拉起（看护每分钟一次）

**预期**：约 3 分钟内出现 `StorageClusterUnhealthy`（warning）、`StorageNodeDown`（work-03）、`StorageDiskDown`（work-03 的 NSD）各一条，`StorageFsUnmounted`（work-03 上的 gp1）一条 critical；恢复后几分钟内全部解除（告警事件页 resolved）；集群概览的健康回到「健康」

## OPS-03 OSD 离线与级别变化（Ceph）

1. `ceph orch daemon stop osd.<work-02 的编号>`
2. 等 4 分钟；再 `ceph osd set-nearfull-ratio 0.01`（让 nearfull 立即出现），等 2 分钟
3. 恢复：`ceph osd set-nearfull-ratio 0.85`、`ceph orch daemon start osd.<编号>`

**预期**：第 1 步后出现集群不健康（warning）与磁盘离线（osd.N）；第 2 步 nearfull 一出现 `CephNearFull`（critical）就触发（不等延迟），健康若变成 error，集群告警先解除 warning 再触发 critical；恢复后全部解除；概览「标志」出现过「容量接近满」后消失

## OPS-04 池用量告警按时触发

1. 把 `gp1` 的配额改小到比已用多一点（编辑存储池），往挂在云服务器上的卷里写数据到 85%，再到 95%；最后删掉写的数据并把配额改回

**预期**：85% 时 `StoragePoolUsageHigh` warning 在一分钟左右出现；95% 时 warning 解除、critical 出现；回到 80% 以下全部解除。`rp1` 同样（Ceph 池到配额时写入会卡住，测到 95% 即可）

## OPS-05 监控曲线

1. 两个集群的「监控」标签，选 1 小时；在一台云服务器里 `dd` 写一阵
2. Prometheus（内网 9090）看 `storage_clusters` 任务的目标、`cloudland_gpfs_*` 与 `cloudland_shared_pool_*` 指标

**预期**：GPFS 有存储池用量、容量、吞吐、IOPS、节点（GPFS 运行中 3、每个文件系统挂载 3）；Ceph 有存储池用量、容量、吞吐、IOPS、OSD（运行 3、在集群内 3）；写数据时吞吐曲线有起伏；`storage_clusters` 的目标是两台 mgr 主机的 9283（只有活动的 mgr 有数据）

## OPS-06 任务的完整日志

1. 打开一个已完成的部署任务，展开安装步骤的一次运行，点「下载完整日志」
2. 把那台节点关机（或拿一个节点离线的运行）再点

**预期**：先显示「正在从节点取回」，几秒内下载 `storage-run-<ID>.log`，内容与节点上 `/opt/cloudland/log/storage/run-<ID>.log` 一致；节点离线时提示节点离线（409）

## OPS-07 GPFS 换盘

1. work-02 加一块回环盘，扫描磁盘；`mmchdisk fs1 stop -d <work-02 的 NSD>` 模拟坏盘，等健康检查报告 down
2. 磁盘表那一行出现「换盘」，选新盘提交

**预期**：只有 down 的那块有「换盘」按钮；任务依次 `核对磁盘` → `建 NSD` → `从文件系统移除磁盘`（`mmdeldisk -p` + `mmdelnsd`）→ `加入文件系统` → `恢复副本`（`mmrestripefs -r`）→ `擦除并释放磁盘`（旧盘没被擦，日志 `not wiping … it failed`）；完成后旧 NSD 不在 `mmlsdisk` / `mmlsnsd`，新 NSD `up`、名字是这台节点的下一个编号，`mmlsattr -L` 的 flags 里没有 `illreplicated`；云服务器 I/O 不中断。`mmdelnsd` 对停掉的盘会打印 `Unable to find disk with NSD volume id` 但返回 0，属正常

3. 负面：盘被报告 down 之后马上 `mmchdisk start` 再提交换盘（赶在下一次健康检查之前）

**预期**：任务在「从文件系统移除磁盘」失败：`<NSD> is recovering: a disk that works is removed the normal way`；再 `mmchdisk stop` 后「重试」任务，从这一步接着跑完

## OPS-08 Ceph 换盘

1. work-02 加一块回环盘，扫描；`ceph orch daemon stop osd.<编号>`，等报告 down
2. 换盘

**预期**：任务 `核对磁盘` → `替换 OSD` → `擦除并释放磁盘`，替换 OSD 一两分钟完成（日志 `marked out osd.N` → `Removed osd.N from host` → `destroyed osd.N` → `Created osd(s) N`）；新 OSD 沿用原编号、`up`、`in`、在 work-02 上；`ceph orch osd rm status` 为空；`ceph -s` 回填完成后 `HEALTH_OK`（回环盘上 30 GB 级别的数据约 25 分钟）

## OPS-09 改角色

1. Ceph：把 mgr 从 work-02 挪到 work-03（先 work-02 去掉 mgr，再 work-03 加 mgr；反过来第一次就会被拒：mgr 最多 2 台），测完挪回去
2. GPFS：给 work-02 加「管理」角色，再去掉

2026-10-04 真实节点验收时发现并修掉的：

19. GPFS 换盘的 `require_down` 原来只拒绝 `up`：盘被 `mmchdisk start` 拉起时是 `recovering`，会被当成坏盘 `-p` 掉。改为只接受 `down` / `unrecovered`（OPS-07 第 3 步）
20. Ceph 换盘永远完不成：`orch osd rm --replace --force` 仍要等 `safe-to-destroy`，3 台主机 × 3 副本时坏 OSD 的数据无处可去，15 分钟超时。改为 `osd out` → `orch daemon rm osd.N --force` → `osd destroy N --force --yes-i-really-mean-it` → 新盘建 OSD → `osd in`（OPS-08，77 秒完成）
21. 同一次故障里级别来回变（严重 → 警告 → 严重）时，第二次严重告警沿用了第一次的指纹，覆盖了第一次的事件记录。改为每次触发各用自己的触发时刻做指纹（OPS-04 里把 gp1 在 81% / 93% 之间来回两次，告警事件页有 4 条）
