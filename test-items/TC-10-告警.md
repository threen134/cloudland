# TC-10 告警（ALM）

优先级 **P1** · 约 30 min

三块**各自独立**，不要混在一起判断：

| 模块 | 接口 | 页面 | 特点 |
|---|---|---|---|
| 节点告警 | `/node-alarm-rules` | `AlarmList.vue` | 每种 `rule_type` **全局只能有一条** |
| VM 告警规则 | `/metrics/alarm/{cpu,memory,bw}/rules` | `VMAlarmRules.vue` | 规则组 + 明细 + 关联虚拟机 |
| 告警事件 | — | `AlarmEvents.vue` | **不是接口创建的**，见下 |

### 事件是怎么来的

Alertmanager 回调 clapi 的 **`POST /api/v1/alerts/process`（无鉴权）**：

- 按 `fingerprint` **幂等 upsert**
- `labels.owner` 必须是 **clapi 本地组织 ID 的字符串**（列表按它过滤）
- `rule_group` 对上规则组才会走通知渠道并产生「发送流水」

## ⚠️ ALM-00 最高优先级前置：Prometheus 规则是全有或全无

节点告警规则的配置**键名必须和 `deploy/roles/monitor/templates/*.yml.j2` 里的变量名一一对上**。

渲染器只认 `{{ x }}` 和 `{{ x | default(y) }}`：

- 名字对不上且**有 default** → 静默退回默认值，**界面上填的阈值一个都不生效**
- 名字对不上且**没有 default** → `{{ x }}` 原样写进规则文件

后者的后果极严重：**Prometheus 加载规则是全有或全无，一个坏文件会让它回滚整份规则集**，此后**所有**告警规则更新都不生效，而且只在 prometheus 容器日志里报 `loading groups failed`。

```bash
ssh work-01 'docker logs cloudland-prometheus --since 30m 2>&1 | grep -i "loading groups failed" && echo "!!! 规则集已回滚" || echo "规则加载正常"'
ssh work-01 'ls /opt/cloudland/deploy/docker/volumes/prometheus/node_templates/*.j2 | wc -l'
ssh work-01 'grep -rn "{{" /opt/cloudland/deploy/docker/volumes/prometheus/rules/ 2>/dev/null | head'
```

- [ ] prometheus 日志无 `loading groups failed`
- [ ] `node_templates/` 下有 **16 个** `.j2` 文件
  > **回归点**：Docker 部署曾从不把 `.j2` 拷进这个目录（只有 Ansible 角色里有），目录是空的 → 创建规则报 `File does not exist`。两个部署脚本已补拷贝步骤。
- [ ] 生成出来的规则文件里**没有残留的 `{{ }}`**
  > 单元测试 `services/alarm_template_test.go` 守这条（`{{ end }}` / `{{ else }}` 等 Go 模板关键字不算）。

## ALM-02 创建节点告警规则

**P0** · 脚本 `alarm-e2e.js`

### 步骤

节点告警页 → 新建 → 选 rule_type → 填配置 → 提交。

### 检查项

- [ ] 创建成功，**不返回 400 `owner is required`**
  > **回归点**：`CreateNodeAlarmRule` 曾把 `owner` 当成客户端必填字段，前端根本不传 → 一律 400。现在从 membership 取。
- [ ] 创建成功，**不返回 500**
  > **回归点**：CPU/内存规则明细曾有 `over` / `down_to` / `down_duration` 三个带 `>= 1` CHECK 约束的字段，而表单没有它们 → 一律 500。而且规则组先落库、明细后失败**没有事务**，留下 0 条规则的孤儿组。这三个字段告警模板从来不用（是自动调整规则的东西），已从模型与接口删除，数据库列留着置 NULL。
- [ ] 同一 `rule_type` 再建一条 → 被拒绝（全局只能有一条）
- [ ] 规则文件写入 `volumes/prometheus/rules/`，prometheus 重新加载成功

### 涉及接口

| 方法 | 路径 |
|---|---|
| GET / POST | `/api/v1/node-alarm-rules` |
| GET / **PATCH** / DELETE | `/api/v1/node-alarm-rules/:id` |

- [ ] **PATCH 在 cpgateway 的代理白名单里**
  > **回归点**：曾漏加，PATCH 一律 404。

## ALM-05 VM 告警规则

**P1** · 脚本 `vmrules-e2e.js`

### 检查项

- [ ] 三种类型（cpu / memory / bw）的规则组都能建、能列出
- [ ] 每个规则组都可达，行能展开看明细
- [ ] 带宽规则的「方向」列显示进 / 出；CPU、内存规则该列显示 `-`
  > **回归点**：`rules` 是 CPU / 内存 / 带宽三种明细的**联合类型**，只有带宽有 `direction`。模板里要用 `'direction' in r` 做类型收窄。
- [ ] 关联虚拟机：CPU / 内存的 `linkedvms` 是 uuid 字符串数组；**带宽的是对象**（`{instance_id, target_device}`）
- [ ] 分页是**真的服务端分页**，不是全量拉回来前端切片

### 名称校验（ALM-05b）

规则组名的前后端规则一致：`^[a-zA-Z][a-zA-Z0-9_]*$`（字母开头，只能字母 / 数字 / 下划线，**不能有连字符**）。

```bash
ssh work-01 'cd /opt/cloudland/deploy/docker && PW=$(grep "^ADMIN_PASSWORD=" .env | cut -d= -f2-)
docker run --rm --network host -v /root/console-test:/work -w /work -e ADMIN_PASSWORD="$PW" \
  mcr.microsoft.com/playwright:v1.55.0-noble node alm3.js 2>&1 | tail -8'
```

- [ ] 名字带连字符（`wp-bad-name`）→ 输入框下红字「名称只能包含字母、数字和下划线」，**保存按钮禁用**
- [ ] 数字开头（`1bad`）→ 红字「名称必须以字母开头」，**保存按钮禁用**
- [ ] 合法名字（`wp_vmrule_1`）→ 无红字，保存按钮可点，创建成功

> **回归点**：按钮的 `:disabled` 原先是 `!createForm.name`（只判断非空），而 `submitCreate` 的守卫是 `isNameValid`（严格正则）且不匹配时**直接 return**。于是名字带连字符时按钮可点、点下去**毫无反应**（红字提示其实在上面，但按钮不禁用会让人以为提交了）。两处条件必须一致。

### 每条阈值的 `name`

`rules[].name` **既不在界面上显示，也不参与生成 Prometheus 规则**（组名、alert 名、rule_id 全部由 `<类型>_<owner>_<组UUID>_<序号>` 推导），只出现在 clapi 的日志和数据库行里。

- [ ] 前端按「组名_序号」自动填充，不让用户填，也不再是空串
  ```bash
  ssh work-01 'docker exec cloudland-postgres psql -U postgres -d cloudland -t -A -F" | " -c \
    "select g.name, d.name from cpu_rule_details d join rule_group_v2 g on d.group_uuid=g.uuid where g.deleted_at is null order by d.id desc limit 3;"'
  ```

### 已知数据卫生问题（不影响功能）

删除规则组是**软删**，但 `cpu_rule_details` / `memory_rule_details` / `bw_rule_details` 里的明细行**不会跟着删**，会持续累积（2026-09-21 实测：28 个软删组留下 24 条 CPU + 1 条内存孤儿明细）。列表查询会 join 存活的组，所以界面上看不到，Prometheus 规则文件也正常删除。

- [ ] 记录当前孤儿行数，确认没有异常增长
