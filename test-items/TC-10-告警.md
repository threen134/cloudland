### 事件是怎么来的

Alertmanager 回调 clapi 的 **`POST /api/v1/alerts/process`（无鉴权，不在 cpgateway 白名单里，只能直连 clapi 的 8255）**：

- 按 `fingerprint` **幂等 upsert**
- `labels.owner` 必须是 **clapi 本地组织 ID 的字符串**（`GET /alarm/events` 按它过滤）；**没有 `owner` 的告警归系统组织**（clapi 里 `org_type=2` 的那一个，work-01 上是 Admin），不再谁也看不到（2026-09-30 改，2026-10-01 已部署，见 ALM-06）
- 节点规则模板渲染时注入 `owner`（系统组织的本地 ID）与 `rule_group`（节点规则的 UUID），这两个值**不能**从规则 config 里设（2026-09-30 改，2026-10-01 已部署）
- `rule_group` 对上规则组、且该组绑了通知渠道，才会发通知并产生「发送流水」

另一个来源是 **VPN 网关**：clapi 直接写事件（`services/vpn_notify.go`），不经 Prometheus / Alertmanager，推给组织下所有启用的渠道，见 ALM-12。

## ⚠️ ALM-00 最高优先级前置：Prometheus 规则是全有或全无

节点告警规则的配置**键名必须和 `deploy/roles/monitor/templates/*.yml.j2` 里的变量名一一对上**。

渲染器只认 `{{ x }}` 和 `{{ x | default(y) }}`：

- 名字对不上且**有 default** → 静默退回默认值，**界面上填的阈值一个都不生效**（现在由 `validateNodeAlarmConfig` 在写入前拒绝，见 ALM-01）
- 名字对不上且**没有 default** → `{{ x }}` 原样写进规则文件（现在 `ProcessTemplate` 渲染后扫描未替换占位符，有就报错、不写文件）

后者的后果极严重：**Prometheus 加载规则是全有或全无，一个坏文件会让它回滚整份规则集**，此后**所有**告警规则更新都不生效，而且只在 prometheus 容器日志里报 `loading groups failed`。

## ALM-06 告警事件

### 注入一条事件

事件只能直连 clapi 投递（网关白名单里没有 `/alerts/process`，经 `$B` 调会被网关拒绝）。

```bash
ssh work-01 'source /root/alarmtest-env.sh
CL=https://10.191.202.40:8255/api/v1
OWNER=$(docker exec cloudland-postgres psql -U postgres -d cloudland -Atc "select id from organizations where uuid=\$\$305fcaf9-c76a-4ed5-a1ae-eddb8d8fc64e\$\$")
cat > /tmp/al.json <<JEOF
{"status":"firing","alerts":[{"status":"firing","fingerprint":"wp-test-fp-001",
 "labels":{"alertname":"wp-test","owner":"$OWNER","severity":"warning","rule_group":"wp-group"},
 "annotations":{"summary":"regression test"},
 "startsAt":"$(date -u +%Y-%m-%dT%H:%M:%SZ)"}]}
JEOF
curl -sk -X POST "$CL/alerts/process" -H "Content-Type: application/json" -d @/tmp/al.json; echo
api GET "/alarm/events?query=wp-test&page_size=100" | jq -c "[.events[]|select(.fingerprint==\"wp-test-fp-001\")|{status,owner,severity}]"'
```
