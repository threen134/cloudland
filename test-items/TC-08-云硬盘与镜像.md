# TC-08 云硬盘与镜像（VOL）

优先级 **P1** · 会创建卷、镜像与临时虚拟机 · 约 50 min（不含 VOL-04 的 30 分钟超时，那一条用改库模拟）

## 设计约定 — 本地数据卷

> **2026-09-22 起卷归属存储池**，池本身的用例在 [`TC-16-本地存储池.md`](TC-16-本地存储池.md)。本文件只管卷与镜像。WDS 已整体删除（备份、一致性组、卷 QoS 都不在了）。

- **创建时不落盘**：`volumes.hyper=0`，直接 `available`；建卷时可以选存储池，不选就是默认池（内置池 `local`）
- **路径由 clapi 下发**，`volumes.path` 是**相对池根**的相对路径：内置池数据盘 `volume/volume-<id>.disk`，其他池 `volumes/volume-<id>.disk`（池根 `/opt/cloudland/pools/<池UUID>`）
- **首次挂载时**才由 `attach_volume_local.sh` 在**虚拟机所在节点**创建（qcow2，2 MiB 簇），并记录 `hyper`；clapi 下发 `new` / `existing`，**`existing` 时文件不在就报错**，不再新建空盘
- 已落盘的卷只能挂给**同节点、且该节点有这个池**的虚拟机
- **状态**：`available` → `attaching` → `attached` → `detaching` → `available`；另有 `resizing`、`deleting`、`delete_failed`、`lost`、`orphaned`、`error`、`pending`（系统盘创建中）。**没有 `in_use`**（2026-09-28 核对 `model/volume.go`）
- **`PATCH /volumes/:id` 按请求体里有没有 `instance` 键区分**：没有 = 挂载不动（只改名）；`"instance": null` = 卸载；`"instance": {"id": ...}` = 挂载。审计动作分别是 `volume.update` / `volume.detach` / `volume.attach`。容量不走 PATCH
- **扩容走 `POST /volumes/:id/resize`**，只能扩大：未落盘的卷只改记录；已落盘的按 `hyper` 下发 `resize_volume_local.sh`——虚拟机开着（运行 / 暂停 / 崩溃）时 `virsh blockresize` **在线扩容、不重启**，关机或未挂载时 `qemu-img resize`；节点失败时回报镜像实际大小（`resize_volume '<id>' 'error' '<GiB>'`），clapi 把容量改回去并恢复可用
- **忙时互斥**：虚拟机处于 provisioning / migrating / rollback / reinstalling / resizing / deleting / rescuing 时拒绝扩容（400，`111005`）；挂载 / 卸载另外还拒绝 `paused`
- **删除是异步的**：接口返回 **202**，卷进 `deleting`，节点回调 `clear_volume` 才删记录；节点回报删除失败时卷回到 `available`（`reason` 以 `delete failed:` 开头）；节点离线直接拒绝；30 分钟没回调转 `delete_failed`（只能再删，不能挂）
- 卸载成功后节点上的磁盘描述文件 `/opt/cloudland/cache/xml/inst-<N>/disk-<卷id>.xml` 会被删除
- 迁移完成后随虚拟机更新 `hyper` 与池
- 删除虚拟机时卷变 `available`、`instance_id` 清空、`hyper` 不变，**卷文件保留**（`lost` / `orphaned` 的卷不动）

> `GET /volumes` 默认**只列数据盘**，要含系统盘得带 `type=all`（配额对账与界面列表都用 `type=all`）。**搜索参数是 `name`**，不是别的列表通用的 `query`（`query` 会被忽略）。

## 前置（2026-09-28 核对）

- **两台测试虚拟机，建在内部子网上**（`mig-int` + 安全组 `mig-vpc-native`，或自建 `wp-` VPC）。**不要建在 `public-756` 上**：公网只剩 1 个空闲地址（`.158`）
  - `wp-vm`：`ubuntu-24.04-minimal`（要有 guest agent，TC-02 建的那台可以直接用），在节点 A
  - `wp-vm2`：cirros 即可，在**另一个**节点 B，只用于 VOL-02
- 虚拟机内部的检查在它所在节点上用 `/root/gexec.sh inst-<N> "<命令>"`（三台都有，经 guest agent）
- 新写的步骤用 `/root/st-env.sh` + `/root/st-lib.sh`（`api_code` 带状态码、401 自动重登；`inst_uuid` / `inst_id` / `inst_hyper` / `vol_uuid` / `vol_row` / `vol_file` / `wait_vol` / `on <hostid>`）。`api_code` 的第三个参数写成 `@/tmp/xxx.json` 时 curl 从文件读请求体。**别在自己的脚本里用 `B` / `T` / `BODY` / `CODE` 这几个变量名**

## VOL-01 创建与挂载

**P1**

```bash
ssh work-01 'source /root/st-env.sh >/dev/null; source /root/st-lib.sh
cat > /tmp/wp-v.json <<JEOF
{"name":"wp-vol","size":5}
JEOF
V=$(api POST /volumes @/tmp/wp-v.json | jq -r .id)
echo "volume=$V"; vol_row $V                      # status|hyper|path|pool_id|size|reason
api GET /volumes/$V | jq -c "{status,path,pool:.storage_pool.name,host:.hypervisor.name}"

I=$(inst_uuid wp-vm); N=$(inst_id wp-vm); H=$(inst_hyper wp-vm)
cat > /tmp/wp-a.json <<JEOF
{"instance":{"id":"$I"}}
JEOF
api PATCH /volumes/$V @/tmp/wp-a.json | jq -c "{name,status}"
wait_vol $V attached; vol_row $V
api GET /volumes/$V | jq -c "{status,target,host:.hypervisor.name}"
on $H "qemu-img info -U $(vol_file $V) | grep -E \"virtual size|cluster_size\"; ls /opt/cloudland/cache/xml/inst-$N/"
on $H "/root/gexec.sh inst-$N \"lsblk -dno NAME,SIZE\""
api GET /instances/$I | jq -c ".volumes"'
```

### 检查项

- [ ] 创建后直接 `available`，`hyper=0`（未落盘），`path=volume/volume-<id>.disk`，`storage_pool` 是 `local`；响应里**没有** `hypervisor`（未落盘时省略；落盘后也只有系统管理员看得到）
- [ ] 挂载请求返回 `attaching`，节点回调后 `attached`（不是 `in_use`）
- [ ] 挂载后 `hyper` 变成虚拟机所在节点的 hostid，`hypervisor.name` 是该节点
- [ ] 节点上出现磁盘文件（路径 = 池根 + `volumes.path`），`cluster_size: 2097152`、虚拟大小 5 GiB
  ```bash
  ssh work-0X 'ls -la /opt/cloudland/cache/volume/'                      # 内置池
  ssh work-0X 'ls -la /opt/cloudland/pools/<池UUID>/volumes/'            # 其他池
  ```
- [ ] `/opt/cloudland/cache/xml/inst-<N>/disk-<卷id>.xml` 存在
- [ ] 虚拟机内 `lsblk` 多一块 5G 的盘
- [ ] 实例详情的 `volumes` 数组里这一项**带 `size`**
- [ ] 盘符是下一个空闲 vdX
  > **回归点**：第二块本地数据卷曾总是分到 vdb（原按 WDS 的 `type='network'` 计数）。挂第二块时确认是 **vdc**。
- [ ] 审计有 `volume.create`、`volume.attach` 两条（`select action, resource_name, status from audit_logs where resource_type='volume' order by id desc limit 5`）

## VOL-03 扩容

**P1** · 在 work-01 上执行（存成 `/root/wp-vol03.sh`）

```bash
source /root/st-env.sh >/dev/null; source /root/st-lib.sh
V=$(vol_uuid wp-vol); I=$(inst_uuid wp-vm); N=$(inst_id wp-vm); H=$(inst_hyper wp-vm)
# 1) never written: only the record changes, nothing is sent to a host
cat > /tmp/wp-v2.json <<'JEOF'
{"name":"wp-vol2","size":1}
JEOF
V2=$(api POST /volumes @/tmp/wp-v2.json | jq -r .id)
cat > /tmp/wp-r2.json <<'JEOF'
{"size":2}
JEOF
api_code POST /volumes/$V2/resize @/tmp/wp-r2.json; vol_row $V2
# 2) attached to the running wp-vm: resized online
cat > /tmp/wp-a.json <<JEOF
{"instance":{"id":"$I"}}
JEOF
api_code PATCH /volumes/$V @/tmp/wp-a.json; wait_vol $V attached
before=$(on $H "/root/gexec.sh inst-$N \"cat /proc/sys/kernel/random/boot_id\"")
cat > /tmp/wp-r8.json <<'JEOF'
{"size":8}
JEOF
api_code POST /volumes/$V/resize @/tmp/wp-r8.json; wait_vol $V attached; vol_row $V
on $H "/root/gexec.sh inst-$N \"lsblk -dno NAME,SIZE; dmesg | grep -i \\\"capacity change\\\" | tail -1; cat /proc/sys/kernel/random/boot_id\""
echo "boot_id before: $before"
# 3) shrinking or the same size is refused
cat > /tmp/wp-r4.json <<'JEOF'
{"size":4}
JEOF
api_code POST /volumes/$V/resize @/tmp/wp-r4.json
api_code POST /volumes/$V/resize @/tmp/wp-r8.json
# 4) detached but written: qemu-img resize on the host
cat > /tmp/wp-null.json <<'JEOF'
{"instance":null}
JEOF
api_code PATCH /volumes/$V @/tmp/wp-null.json; wait_vol $V available
cat > /tmp/wp-r9.json <<'JEOF'
{"size":9}
JEOF
api_code POST /volumes/$V/resize @/tmp/wp-r9.json; wait_vol $V available
on $H "qemu-img info -U $(vol_file $V) | grep \"virtual size\""
```

### 检查项

- [ ] **未落盘**的卷扩容：200，状态一直是 `available`，`size` 改成 2，cland 日志里没有这次的 `resize_volume_local.sh`
- [ ] **已挂载在运行中虚拟机上**：200，状态 `resizing` → `attached`；虚拟机内 `lsblk` **立即**看到 8G、dmesg 有 `capacity change`，`boot_id` 前后相同（不重启）
- [ ] 缩容与同容量都返回 **400**，`error_code` **121008**（`The size must be greater than the original size`）
- [ ] **已落盘但未挂载**：节点用 `qemu-img resize`，镜像虚拟大小变成 9 GiB，卷回到 `available`
- [ ] 系统盘（`booting=true`）扩容时 `instances.disk` 同步变成新容量（对 `wp-vm` 的系统盘 `instance-<N>-boot-volume` 扩 1 GB 验证；Ubuntu 带 cloud-init，重启后根分区自动扩）
- [ ] 网关磁盘用量按差值增加（`org_resource_consumptions.disk_gb`，见 VOL-07 的查询）
- [ ] 审计动作 `volume.resize`
- [ ] 池里放不下时 409（`122003`，消息带池名与机器名）——内置池一般放得下，这条在 TC-16 STO-10 的小池上做

> 失败回滚与状态拦截见 VOL-12。

## VOL-04 卸载与删除

**P1** · 在 work-01 上执行（存成 `/root/wp-vol04.sh`）

```bash
source /root/st-env.sh >/dev/null; source /root/st-lib.sh
V=$(vol_uuid wp-vol); V2=$(vol_uuid wp-vol2); I=$(inst_uuid wp-vm); N=$(inst_id wp-vm); H=$(inst_hyper wp-vm)
cat > /tmp/wp-a.json <<JEOF
{"instance":{"id":"$I"}}
JEOF
cat > /tmp/wp-null.json <<'JEOF'
{"instance":null}
JEOF
# attached volumes can not be deleted
api_code PATCH /volumes/$V @/tmp/wp-a.json; wait_vol $V attached
api_code DELETE /volumes/$V                                   # 400 121012
# detach: the description file goes, the volume file stays
api_code PATCH /volumes/$V @/tmp/wp-null.json; wait_vol $V available; vol_row $V
F=$(vol_file $V); on $H "ls /opt/cloudland/cache/xml/inst-$N/; ls -la $F"
# delete the written volume: 202, the host removes the file
api_code DELETE /volumes/$V; vol_row $V
sleep 10; q "select deleted_at is not null from volumes where uuid='$V'"; on $H "ls -la $F"
# never written: 204, gone at once
api_code DELETE /volumes/$V2; q "select deleted_at is not null from volumes where uuid='$V2'"
```

另建 `wp-vol4`（1 GB），挂到 `wp-vm` 再卸下（已落盘、`available`），做三个失败分支：

```bash
V4=$(vol_uuid wp-vol4); F4=$(vol_file $V4)
# a) the host fails to delete: rm of an immutable file fails
on $H "chattr +i $F4"; api_code DELETE /volumes/$V4; sleep 10; vol_row $V4
on $H "chattr -i $F4"
# b) no answer for 30 minutes, simulated: mark it deleting long ago (no command is sent)
q "update volumes set status='deleting', updated_at=now()-interval '31 minutes' where uuid='$V4'"
sleep 90; vol_row $V4
api_code PATCH /volumes/$V4 @/tmp/wp-a.json                   # attach refused
api_code DELETE /volumes/$V4; sleep 10; vol_row $V4; on $H "ls -la $F4"   # deleted for real
# c) host offline: create and write wp-vol5 the same way, then for a moment set the host to 10
q "update hypers set status=10 where hostid=$H"; api_code DELETE /volumes/$(vol_uuid wp-vol5)
q "update hypers set status=1 where hostid=$H"
```

### 检查项

- [ ] 挂着的卷删除 → **400**，`error_code` **121012**（`... is attached to an instance, please detach it first`）
- [ ] 卸载后 `status` 回到 `available`、`instance_id=0`、`target` 为空、`hyper` **不变**，节点上的磁盘描述文件被删，卷文件还在
- [ ] 已落盘的卷删除返回 **202**，卷经 `deleting`，节点回调后记录消失（`deleted_at` 非空）、磁盘文件被删
- [ ] 未落盘的卷删除返回 **204**，立即消失
- [ ] 节点删文件失败（a）→ 卷回到 **`available`**，`reason` 为 `delete failed: failed to delete ...`（**不是** `delete_failed`，2026-09-28 核对 `HandleClearVolume`）
- [ ] 30 分钟没回调（b）→ 后台任务（每分钟一轮）把它改成 **`delete_failed`**，`reason` 为 `the host did not confirm the deletion`；此时挂载 → 400 `121007`；再次删除 → 202 → 记录消失、文件被删
- [ ] 节点离线（c，`wp-vol5` 已落盘，库里临时把该节点 `hypers.status` 改成 10）时删除被**直接拒绝**：400，`error_code` 171005，`<host> is offline, the volume file can not be deleted now`，卷仍是 `available`；**几秒内改回 1**（这台节点上还有保留环境）
- [ ] 删除 202 时网关**立即释放**磁盘配额（`FinishQuota` 把 202 当成功）；审计 `volume.delete` 状态 202

## VOL-06 镜像导入

**P1** · work-01 是 **S3 模式**（`S3_ENDPOINT=images.cloudland.internal:9000`）：由 **clapi 容器**下载 `download_url` 写进 MinIO，再识别格式

```bash
ssh work-01 'source /root/st-env.sh >/dev/null
cat > /tmp/wp-img.json <<JEOF
{"name":"wp-img","download_url":"https://download.cirros-cloud.net/0.6.2/cirros-0.6.2-x86_64-disk.img",
 "os_code":"linux","os_family":"linux","os_version":"0.6.2","user":"cirros","boot_loader":"bios"}
JEOF
api_code POST /images @/tmp/wp-img.json'
```

必填：`name`（2–32 字符）/ `download_url`（`http_url`）/ `os_code`（**只能是 `linux` / `windows` / `other`**，原用例写的 `cirros` 会 400）/ `os_family` / `os_version`（2–32）/ `user`（2–32）/ `boot_loader`（`bios` / `uefi`）。

- [ ] 创建返回 200，状态 **`creating`**（不是 `pending`），下载完成后 `available`，`format` 为 `qcow2`、`size` 为虚拟大小
- [ ] 下载地址不通 / 返回非 200 / 内容既不是 qcow2 也不是 raw 时变 `error`，MinIO 里不留对象
- [ ] `available` 后能用于创建虚拟机
- [ ] 需要 clapi 容器能访问该地址（2026-09-28 核对：work-01 的 clapi 容器能访问，这个地址 302 跳到 GitHub 下载，Go 的 HTTP 客户端会跟随）；换环境访问不了就换一个内网可达的 HTTP 地址

### URL 校验

```bash
ssh work-01 'source /root/st-env.sh >/dev/null
for bad in "http://x/a b.img" "http://x/a$(printf "\t")b.img" "http://x/a -o /root/.ssh/authorized_keys"; do
  jq -n --arg u "$bad" "{name:\"wp-bad\",download_url:\$u,os_code:\"linux\",os_family:\"linux\",os_version:\"0.6.2\",user:\"cirros\",boot_loader:\"bios\"}" >/tmp/wp-bad.json
  api_code POST /images @/tmp/wp-bad.json | cut -c1-120
done'
```

- [ ] `download_url` **禁止空白与控制字符**，三条都返回 400，库里没有 `wp-bad`
  > **回归点**：`http_url` 校验允许空格，曾可拼出 `curl ... -o /root/.ssh/authorized_keys`。见 `TC-13 SEC-02`。

## VOL-07 镜像可见性与配额

**P1**

- [ ] 系统管理员（`X-System-Role=1`）创建的镜像被 clapi **强制设为公共**（`public=true`），网关不扣镜像配额
- [ ] 普通成员（非系统管理员）创建的镜像是**私有**的，扣 1 个镜像配额；删除时释放；超过 `max_images` 返回 429 `quota_exceeded`
- [ ] 删除时网关先 GET：`public=true` 的不释放
- [ ] 对账用 `GET /images?owned=true&visibility=private`（`owned` 只看本组织，不受管理员身份影响）
- [ ] 普通成员的列表 = 本组织的 + 公共的；系统管理员不带 `owned` 时看到全部
- [ ] 只有系统管理员能 `PATCH /images/:id {"public": ...}`，其他人 403；改可见性**不即时记账**，下次登录对账才反映
