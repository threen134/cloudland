## 发现并修掉的问题

都已推到 work-01 / 三台节点验证过，**未提交**。编号与 `TC-21` 的「历史缺陷回归点」接着排（9–13）。

| # | 问题 | 修法 |
|---|---|---|
| 9 | Ubuntu 24.04 的 `cephadm` 19.2.3 包不依赖 `python3-jinja2`，而 cephadm 要 import 它：bootstrap 一启动就 `ModuleNotFoundError: No module named 'jinja2'`（26.04 的沙箱里碰巧装着，没暴露） | `ceph_install.sh` 给守护进程节点多装 `python3-jinja2` |
| 10 | 建 OSD 前等「这台主机有设备清单」永远等不到：19.2 的清单是 `ceph-volume inventory --filter-for-batch`，只列可用的盘，这三台的 sda（系统盘）、sdb（GPFS）、回环盘都不可用，清单就是空的、永远是空的；而 19.2 的 `daemon add osd` 根本不按清单校验，也没有 `--skip-validation` 参数 | 去掉等待，直接 `daemon add osd`；只在 20.2 那种按清单校验、报 `No devices found for host` / `is not found on host` 时才带 `--skip-validation` 重试 |
| 11 | 中止的部署删不掉：删除时只在「已经是成员」的管理节点里选执行者，中止的部署里节点都还是 `joining`，接口报「The cluster has no admin host」 | 删除集群时管理节点不按状态过滤（与 GPFS 一样）；PostgreSQL 测试 `TestStorageCephAbortedDeletePG` |
| 12 | 回到 20.2（WSL 沙箱）复测时发现：20.2 的 `orch daemon add osd` 每次都把那块盘存成**受管**的规格 `osd.default` 并立即应用（cephadm 判断规格是否已存在时拿 `default` 比 `osd.default`，永远不等），按代码这块盘移除、清掉之后后台会在上面重新建 OSD（没有实测）。19.2 没有这个规格 | 建完 OSD 后 `orch set-unmanaged osd.default`（19.2 上命令失败、无害）。推到三台后 CEPH-09 重跑：加盘 osd.3 两分钟 up、移除 80 秒，`HEALTH_OK`、盘为空闲；WSL 20.2 端到端测试通过两次，保留集群那次 `osd.default` 是 `<unmanaged>` |
| 13 | CEPH-12 第一次重启时，s2-01 的 RBD 写入在 work-03 关机那一刻卡了 13.4 秒。work-03 的日志：osd.2 收到 SIGTERM 后马上向 mon 报告下线（`prepare_to_stop telling mon we are shutting down`），16 毫秒后同一台机器上的 mon.work-03 也开始关闭，消息丢了，osd.2 等满 5 秒确认超时才停；集群靠另外两个 OSD 的心跳超时才把它标 down。systemd 关机时把一台机器上的 mon、OSD 一起停，Ceph 软件包的单元把 OSD 排在 mon 之后正是为此，cephadm 写的单元没有 | 安装步骤给守护进程节点写 systemd drop-in `ceph-<集群>@.service.d/cloudland-order.conf`（`After=ceph-<集群>@mon.%l.service`，`%l` 是短主机名，cephadm 按它给 mon 起名；mon 单元自己读到时 systemd 丢掉这条自依赖并记一行警告），删除集群时删掉（`backends/ceph.sh` 的 `ceph_unit_order` / `ceph_unit_order_remove`）。推到三台、对现有的 ceph1 调了一次。对比（`systemctl stop ceph-<集群>.target`，与关机的停止顺序同一套机制）：没修时 OSD 等确认 5 秒、17.6 秒后标 down、rb-b 卡 13.5 秒；修后 1.3 秒得到确认、2.7 秒标 down、卡 1.6 秒；再真实重启一次也是 1.6 秒。WSL 端到端测试加了「OSD 排在本机 mon 之后」与「删除后不残留 drop-in」两项检查，通过 |

另外，20.2 复测第一次失败（OSD 建出来但一直 down、后台每分钟重放规格）**不是代码问题**：WSL 里残留着节点脚本测试 `stc-test2.sh` 建的假 OSD 卷 `ceph-1111aaaa-…/osd-block-x`（只有 `ceph.osd_id`、`ceph.cluster_fsid` 两个标签），20.2 的 `ceph-volume lvm list` 遍历所有逻辑卷、读不到 `ceph.type` 就崩溃，cephadm 看不到刚建的 OSD、也不部署守护进程。这个测试已改为补全标签，并在退出时删掉卷组、卸下回环设备。
