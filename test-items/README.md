# CloudLand 回归测试套件

本目录是 CloudLand 的回归测试清单。每个文件对应一个功能域，内含可直接执行的步骤、明确的检查项、涉及的接口，以及**历史缺陷回归点**（曾经真实出过问题、必须每轮复查的地方）。

## 怎么用

1. 先读 [`00-环境与前置.md`](00-环境与前置.md)，把环境准备好：登录函数（`st-env.sh`）、界面测试方式（**本机 5173 + 本机 Playwright**，写请求兜底拦截）、配额、**保留资源禁改清单**与**公网 IP 只剩 1 个**的约束，并做一份**基线快照**（§4.3）。
2. 按下表与「执行顺序」一节执行。`P0` 必跑；`P1` 建议跑；`P2` 仅在改动涉及该域时跑。
3. 每个用例做完按「清理」小节收尾，最后跑 [`00-收尾检查.md`](00-收尾检查.md) 确认环境回到基线。

## 用例编号

`<域缩写>-<两位序号>`，例如 `LB-04`。编号一经分配不复用，废弃的用例标注「已废弃」保留占位，便于对照历史执行记录。收尾检查的 `C-xx` 同样不复用。

## 回归功能追踪表

[`回归功能追踪.csv`](回归功能追踪.csv)（UTF-8 带 BOM、CRLF，Excel 可直接打开）是整套回归测试的追踪表：**每行是一个子功能**，覆盖平台全部功能域（虚拟机、网络、存储、控制面、界面……），列出功能描述、回归用例、覆盖步骤、最近一次执行记录和测试结果。2026-10-12 先按共享存储建表，2026-10-14 起按设计文档与代码逐个功能域核对用例后扩展到全部功能（原文件名 `共享存储功能追踪.csv`）。

- 列：功能域、大功能、子功能、功能描述、设计依据、回归用例（`TC-xx 用例编号`）、覆盖步骤、最近执行（`runs/` 下的执行记录名）、测试结果。
- **设计依据**（2026-10-14 加）：这一行的预期依据设计文档的哪一节，按功能域对齐时填，没对齐的域先空着。写法用「；」分隔多项：
  - `<文档>.md §<章节号> <标题或条目名>`，同一行后面的项可以省略文档名，表示同一份。例：`cpgateway-go-migration-plan.md §1.6 组织管理 API Handler；§13 成员角色`
  - 章节号在一份文档里有重复时（如 cpgateway 设计的两个 3.1）必须带标题；§13 这类表格写表格行的名字
  - 没有设计依据的写 `代码：<路径>[、<路径>]，无设计`
  - 覆盖检查脚本会校验文档、章节、标题或条目名、代码路径都存在；被引用的设计文档末尾有一节「回归用例对照」，由 `python test-items/scripts/check_route_coverage.py --update-design-maps` 从这一列生成，改了这一列要重新生成（CI 会查两边是否一致），不要手改那张表
- 结果取值：`通过`；`部分通过：<没覆盖的部分>`；`失败：<现象>`；`仅沙箱`（只有 PostgreSQL / WSL / 单元 / 本机界面模拟，没在真实节点上跑过）；`未测：<原因>`；`SKIP：<原因>`。
- 「测试结果（基线：1.1.0 之前，截至 2026-10-14）」（1.1.0 之前各组件没有统一的版本号）是各轮执行到 2026-10-14 为止的结果。⚠️ 共享存储（TC-20–26）的结果来自 2026-10-02 重装后的 work-x；其余功能域的结果来自重装**之前**的环境（主要是 `runs/2026-09-28-97422374+全量回归.md` 与 `runs/2026-09-30-97422374+修复部署.md`），新环境上还没重跑。
- 每次发版在最右边加一列「测试结果（<版本> <提交> <日期>）」，<版本> 就是仓库根 `VERSION` 的内容（clapi、cpgateway、前端都取它，见 `TC-01` BUILD-14），<提交> 是部署到测试环境、填结果所依据的那次构建的 commit（短哈希），<日期> 是最后一次填写的日期，按回归用例重跑后填写。回归中修了问题、重新部署后，<提交> 改成修复后的构建，修复后复测过的格子不加标记，只在修复前构建上测过、之后没重测的格子末尾标「〔修复前构建〕」，同一行几条用例两种都有时写「〔X、Y 为修复前构建〕」；修复前构建的 commit 写在这一版的执行记录里（1.1.0：修复前 `14b01d66`、修复后 `64974e5c`，见 `runs/2026-10-14-v1.1.0+全量回归.md`）；新增功能加行，新增用例同时写进「回归用例」与「覆盖步骤」。用例里标「2026-10-14 按代码核对补，未执行」的是这次核对补的，结果一律从「未测」起步。

### 接口覆盖检查

`python test-items/scripts/check_route_coverage.py`（GitHub Actions 的 `route-coverage` 任务每个 PR 都跑）列出全部对外接口（cpgateway 自有路由 + 代理白名单），检查每个接口在用例或追踪表里以「方法 + 路径」出现过（如 `` `POST /instances/:id/reinstall` ``，参数可写 `:id` / `<id>` / `{id}` / 实际值，`/api/v1` 前缀可有可无，`.../reinstall` 这种省略写法也算）。

- `scripts/route_coverage_baseline.txt`：**已知缺口**，2026-10-14 建立时 319 个接口里有 113 个没有用例明确写到（同日对齐「权限、组织与配额」补了 13 个，剩 100 个；对齐「虚拟机生命周期与存储」补了 15 个、删掉一个不存在的白名单路由，剩 84 个；对齐「网络」补了 24 个、删掉 4 个从来没通的白名单路由，剩 56 个）。按功能域对齐时逐个补用例，补上后**从基线里删掉那一行**（不删检查会失败，提醒基线只减不增）。
- `scripts/route_coverage_exempt.txt`：有意不追踪的接口，每行要写理由，现在是空的。
- 新增对外接口而没有用例，检查失败；不要把它加进基线，去写用例。`--report` 打印完整的覆盖 / 缺口表。
- 只说明「接口被提到」，不说明预期写得对、跑过没有；后两件事看用例的依据与追踪表的结果。
- **白名单路由必须在 clapi 存在**（2026-10-14 加）：`proxy_routes.go` 每一条转发的目标路径要在 `api/src/apis/routes.go` 注册过，否则网关转过去 clapi 回 404，或者落到同位置的参数路由上（`/instances/rule-links` 曾落到 `/instances/:id`）。已知的错配记在 `scripts/proxy_unrouted_baseline.txt`（2026-10-14 对齐网络后已清空），新出现的直接失败。
- 路由只从 `cpgateway/src/apis/routes.go` 与 `proxy_routes.go` 读。脚本认不出的注册写法（`Handle`、`Any`、写在别的文件里）直接报错，要么改成 `routes.go` 里的常规写法，要么教脚本认它；路径参数（`:id`）不会匹配同一位置上兄弟路由的固定段（`batch_attach` 不算覆盖 `:id`）。

## 通过标准

一轮回归判定为**通过**，需同时满足：

- 所有 P0 用例的检查项全部通过，无 `FAIL`。
- P1 用例的失败项都有对应的缺陷记录，且经确认不是本次改动引入。用例里标了「已知问题」的（例如 2026-09-28 补测的 FAIL-1..9）按已知处理，不算新缺陷，但结果仍如实记 `FAIL`。
- 标着「**2026-09-30 已修（…），2026-10-01 已部署，按本条判定**」的检查项：被测环境还没部署这批修复时，按原记录的已知问题处理（如实记 `FAIL`、不算新缺陷）；**部署之后**按改写后的新预期判定，再失败就是修复没生效，要当新问题报。界面类的修复在本机 5173 上就能按新预期验证。修复清单与复测对照见 `runs/2026-09-28-97422374+全量回归.md` 的「2026-09-30 修复进展」，部署要点见 `00-环境与前置.md` §8.1。
- 收尾检查全绿：测试资源清零（C-01）、基线快照比对无差异（C-15）、保留资源完好（`rb-*` 负载均衡环境、`mig-*` 迁移环境、`ibmx` / `ibmr` / `aax` 与 `a1` 四个 VPN 网关及 IBM Cloud 对接环境、来历未记录的 `net-*` / `big-vm` / `r1..r9`）、三节点在线、测试临时容器已删。

任何一条 P0 失败即判定**不通过**，不允许以「与本次改动无关」为由放行 —— 先定位是谁引入的。因环境限制（公网 IP 不足、破坏性）跳过的 P0 检查项要逐条写明理由，并在结论里说明「未覆盖」。

## 记录方式

每轮执行在 `runs/` 下按 [`runs/模板.md`](runs/模板.md) 建一个 `YYYY-MM-DD-<被测版本 commit>[+<主题>].md`，逐条记 `PASS` / `FAIL` / `SKIP` 与证据（命令输出、截图路径）。`FAIL` 必须附上定位结论。开始前的基线（健康检查输出、基线快照文件名、C-08 的系统设置、C-10 的比对结果）也记在里面，收尾时拿来比。

## 维护约定

- **修一个 bug，就往对应文件的「历史缺陷回归点」加一条**，写清现象、根因、判定方法。这是本套件最有价值的部分。
- 新增接口或页面时补对应用例；删除功能时把用例标注「已废弃」而不是删掉。
- 环境基线变了（保留资源增删、公网 IP 占用、部署状态），同步改 `00-环境与前置.md` §1、§4 与 `00-收尾检查.md` 里的参考值。
- 自动化脚本：API 脚本放 work-01 的 `/root/*.sh`；界面脚本在**本机**对 5173 跑（放会话临时目录，会话结束就没了，要保留的副本放 work-01 `/root/console-test/`）；work-01 上的 Playwright 容器只用于已部署界面。文件名在用例里注明。**脚本是用例的实现，不是替代**：脚本跑通不等于用例通过，检查项仍需逐条确认。
- 执行回归**不部署**：要部署时停下来问用户（`00-环境与前置.md` §8）。
